## (1) #14 分頁修法的回歸檢查（PostgREST 1000 列上限）

修法（PR #132）已在 09-15 daily 通過 prod 驗證：run `34922445049` 印出 `get_existing_title_fingerprints：取得 1837 筆`。本週起是回歸檢查。

- 每個 run 找 `get_existing_title_fingerprints：取得 N 筆`（週報可能印不只一次，每次都算；它查的是整張 articles 表，所以每次都應 > 1000）。**這行不存在**、任何一次 N ≤ 1000、或出現 `跨週指紋查詢失敗` → FAIL。
- 列出每個 run 的 `get_traffic_buffer：取得 N 筆`（週報會印兩次；09-14 週報是 877／923，09-15 daily 是 843）。任何 N 恰好是 1000 → 特別標出：那是修法前的截斷值，修法後出現的機率極低，交棒本地確認。

## (2) #13 的 429 還在不在

- 每個 daily 與週報：數以 `[embedding] 生成失敗：`（含冒號）開頭的行數，並逐字引用 `[embed_dedup] N/M 篇候選的向量生成失敗` 那行；沒有就寫沒有。
- ⚠️ 計數陷阱：彙總 warning 本身也含「[embedding] 生成失敗」這幾個字——只數帶冒號的逐筆行。
- ⚠️ 不要用裸字串 `429` grep 計數：它會命中 URL 編碼連結與時間戳裡的數字。
- 每個 daily 與週報：逐字引用 `[embedding] 重試共等待 N/60 秒` 那行（PR #137 起才有；有重試才印，預算不夠時後面會接「k 篇因預算不足不再重試」）；沒有就寫「無重試」。
- ⚠️ 判讀陷阱：`生成失敗：` 行數變少**不等於** 429 消失——也可能是 429 發生了但被重試救回。這兩種情況只能靠上一條的「重試共等待」行分辨，兩行要一起報。
- 對照：09-08～09-14 只有 09-11 出現（42/170），其餘 0，週報 0。⚠️ 那是 PR #137（09-16 merge）**之前**的數字：當時沒有重試，429 一次就算失敗；之後只有重試完仍失敗才算，兩者不能直接比。

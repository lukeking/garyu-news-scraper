## (1) GNS-014 分頁修法的回歸檢查（PostgREST 1000 列上限）

PR #132 替兩個查詢都加了分頁。指紋那半 09-15 起每個 run 都 > 1000（10-26 週報是 2312／2330），本週是回歸檢查；buffer 那半**在 prod 還沒被行使過**，見第二條。

- 每個 run 找 `get_existing_title_fingerprints：取得 N 筆`（週報可能印不只一次，每次都算；它查的是整張 articles 表，所以每次都應 > 1000）。**這行不存在**、任何一次 N ≤ 1000、或出現 `跨週指紋查詢失敗` → FAIL。
- 列出每個 run 的 `get_traffic_buffer：取得 N 筆`（週報會印兩次；10-26 週報是 878／896，10-20～10-25 daily 是 833～910）。
  - 任何 N > 1000 → 逐字引用並標出：這是 buffer 分頁第一次在 prod 生效的證據，不是風險。
  - 任何 N 恰好是 1000 → 特別標出：那是修法前的截斷值，修法後出現的機率極低，交棒本地確認。
  - ⚠️ 判讀陷阱：GNS-014 當初「約 09-28 撞線」的估計是 PR #132 **之前**的外推。分頁之後 N 過 1000 是正常的，不要把「接近 1000」寫成撞線風險。

## (2) GNS-013 的 429 還在不在

- 每個 daily 與週報：數以 `[embedding] 生成失敗：`（含冒號）開頭的行數，並逐字引用 `[embed_dedup] N/M 篇候選的向量生成失敗` 那行；沒有就寫沒有。
- ⚠️ 計數陷阱：彙總 warning 本身也含「[embedding] 生成失敗」這幾個字——只數帶冒號的逐筆行。
- ⚠️ 不要用裸字串 `429` grep 計數：它會命中 URL 編碼連結與時間戳裡的數字。
- 每個 daily 與週報：逐字引用 `[embedding] 重試共等待 N/60 秒` 那行（有重試才印，預算不夠時後面會接「k 篇因預算不足不再重試」）；沒有就寫「無重試」。

- 任何 run 出現「因預算不足不再重試」→ 在表下標出是哪天、幾篇。
- 對照（10-20～10-26）：7 個 run 生成失敗都是 0、無重試（10-06～10-19 也是）。最近一次沒救回是 09-30（1 篇 503，`重試共等待 59/60 秒，1 篇因預算不足不再重試`）；09-23、09-25 的 429 都被救回。

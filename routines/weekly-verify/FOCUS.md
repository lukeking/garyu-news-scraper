`#225` 讓週報流程的三支程式（`main.py`、交通分析、術語收錄）多了一個不發布的模式，只有手動觸發的 `weekly-dry-run.yml` 會設。排程的兩支週報（`weekly-traffic.yml`、`weekly-ffxiv.yml`）與 `auto-kb.yml` 沒設，行為應該跟以前一樣。

**先判斷本週適不適用**：`gh pr view 225 --json state,mergedAt`，兩支週報各跑一次 `gh run view <ID> --json event,createdAt`。

- `state` 不是 `MERGED`，或 `mergedAt` 晚於本週週報的 `createdAt` → 寫「`#225` 還沒在本週週報之前 merge，(0) 不適用」，往下做 (9)。
- 某一支的 `event` 不是 `schedule` → 照樣做下面，在本節標出是哪一支不是排程觸發的。
- 其餘 → 做下面四條，結果列在本節。

1. 兩支週報的 log 各數一次含 `[不發布]` 的行（`grep -F '[不發布]'`）。預期都是 0 行。**有任何一行** → FAIL，逐字引用前 10 行，標在報告最前面：正式的週報走進了不發布的模式，寫入或發布可能被略過。
2. 下面每一種行各數幾行，列成表。交通那一支：`✓ traffic buffer upsert 完成：`、`已清理過期 buffer：`、`✓ hot_topic_report upserted:`、`✓ hot_topics.json 已寫入：`。FFXIV 那一支：`✓ Supabase upsert 完成：`、`=== 發布完成（`。
   （11-23 是拆開後第一次排程：交通 run `45112686692`、FFXIV run `45124546806`，六種行各 1 行。）
   某一種是 0 行 → 跟 11-23 那兩支比；上一次有、本週沒有 → 標出（不判 FAIL：那一週可能本來就沒有熱點或彙整，本地讀回時判）。
3. 兩個部署步驟：各自 `gh run view <ID> --json jobs`，交通那一支的 `Deploy Traffic Pages to Cloudflare`、FFXIV 那一支的 `Deploy FFXIV Pages to Cloudflare`，`conclusion` 都是 `success` → ✅；其他值 → 標出。
4. 術語收錄的連帶觸發：`gh run list --workflow auto-kb.yml --limit 5 --json databaseId,createdAt,event,conclusion`。`auto-kb.yml` 只認 FFXIV 那一支的名字，FFXIV 那一支一結束（不論成不成功）就會有一個 `event` 是 `workflow_run` 的 run；術語收錄有沒有真的跑，看那個 run 的 `conclusion`。`success` → ✅，寫出它的 ID，並數那一次 log 裡含 `[不發布]` 的行（預期 0 行，有 → 同第一條，FAIL）；`skipped` → 標出：術語收錄沒有跑（FFXIV 那一支沒有成功結束時 job 會被跳過，一併寫出 FFXIV 那一支的 `conclusion`）；其他值 → 標出，寫出那個值；沒有這個 run → 標出（FFXIV 那一支還沒結束或不存在，一併寫出它的狀態）。本週一之後有兩個以上 `workflow_run` 的 run → 標出（交通那一支不該觸發它）。

## (1) GNS-014 分頁修法的回歸檢查（PostgREST 1000 列上限）

PR #132 替兩個查詢都加了分頁。指紋那半 09-15 起每個 run 都 > 1000（11-23 是交通那一支 2421、FFXIV 那一支 2306），本週是回歸檢查；buffer 那半**在 prod 還沒被行使過**，見第二條。

  - 任何 N 恰好是 1000 → 特別標出：那是修法前的截斷值，修法後出現的機率極低，交棒本地確認。

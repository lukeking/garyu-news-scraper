# Feature Specification: 補政策 digest 的來源

**Feature Branch**: `014-policy-source-expansion`  
**Created**: 2026-10-13  
**Status**: Draft  
**Input**: BACKLOG `GNS-008` 重開——常設重開條件（任意連續三週裡 L1 有兩週未過）在 10-12 成立
（09-28 ❌／10-05 ✅／10-12 ❌），2026-10-13 Luke 裁示開 spec 補來源。`GNS-20261005-crb` 併入當前置。

## 背景：為什麼這次是「補來源」

013 把兄弟政策類別（`路權政策`／`科技執法`／`交通工程`）匯流進 `道安政策` digest，解的是
「政策內容被分類法切碎在門檻之下」。它把既有內容用滿，但不會無中生有——013 自己的「已知限制」
預測過：兄弟類別的量一抖，承重就回到匯流前。逐週實測（抽掉最大來源後剩幾篇，門檻 `trigger_count` 10）：

| 週 | 08-24 | 08-31 | 09-07 | 09-14 | 09-21 | 09-28 | 10-05 | 10-12 |
|---|---|---|---|---|---|---|---|---|
| 匯流後 | 7 ❌ | 13 | 11 | 12 | 21 | 7 ❌ | 20 | 6 ❌ |
| 不匯流（反事實） | 0 | 7 | 4 | 4 | 12 | 3 | 10 | 2 |

不匯流的反事實八週有六週 < 10；最大來源 `Google News 交通安全教育` 在 10-12 佔匯流後池的 75.0%、
不匯流的 89.5%。單一 feed 依賴是結構性的，匯流只是在多數週把它撐過門檻。10-12 那個 ❌ 已確認
不是 `embed_dedup` 比對窗放寬（`GNS-20261005-nwn` 方向 A）造成的（BACKLOG `GNS-008` 觀測記錄 10-12）。

**這次不能重蹈 07-20 的覆轍。** 07-20 加了六個政策來源，三週後進政策池的 91 篇裡 88 篇仍是
`交通安全教育`。原因不是產量：

- 分類是先命中先贏（`科技執法` → `路權政策` → `交通工程` → `道安政策` → … → `行人事故` → `路口安全`）。
  標題帶 `行人`／`路口` 這類 token 就落在事故類，不在匯流範圍內。
- `source_defaults`（來源 → 預設類別）只在標題分不出類時才生效。
- 收集端還有一關：沒有 `機車` 字眼的稿子會在相關性檢查被整批擋下，除非來源設成豁免。

所以「加了來源」與「內容會進 digest 池」是兩件事，本 spec 要求的是後者。

**現有來源也有同一個問題，而且形狀不只一種**（2026-10-13 實測，當期樣本，唯讀）。`source_defaults` 已把
`報導者`、`天下` 對映到 `道安政策`，但兩者都沒設相關性豁免：

- `Google News 報導者交通`：6 篇全被相關性檢查擋下，其中 3 篇是正題（通學環境交通安全大體檢），3 篇離題（政黨、少年版）。
- `Google News 天下交通`：17 篇全被擋下，**17 篇都離題**（長照、國旅、選舉、AI 工具）——這裡相關性檢查擋得對。

所以缺的不只是來源，還有 query 的精度：query 太寬，就只能靠「機車」這把粗篩子擋雜訊，好稿跟著被擋。
「豁免後會進池幾篇」不足以判斷一個來源，還要看進來的是不是正題。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 政策彙整的深度不再繫於單一 feed (Priority: P1)

讀者每週收到的「道安政策 · 彙整」，池子大部分來自同一個 Google News query。那個 query 改變行為或
被限流時，報告會直接消失，而唯一的徵兆是報告不再出現。使用者要的是：就算抽掉最大的那個來源，
其餘來源每週也撐得過觸發門檻。

**Why this priority**: 這是本 spec 唯一的目的，也是 `GNS-008` 重開條件量的那件事。

**Independent Test**: 讀週報 log 的 `digest[道安政策] 最大來源：… 抽掉最大剩 N` 那一行（10-05 起每週都有），
與 `trigger_count` 比。週驗收 routine 已經每週判定。

**Acceptance Scenarios**:

1. **Given** 新來源已上線，**When** 週報執行，**Then** 抽掉最大來源後剩下的篇數 ≥ `trigger_count`。
2. **Given** 新來源全部停用，**When** 週報執行，**Then** 行為與本 spec 之前相同（變更可回滾）。

---

### User Story 2 - 來源清單的現況在 repo 裡看得到（前置） (Priority: P1)

現在「哪些來源在餵管線」只存在 GitHub 變數裡（`GNS-20261005-crb`）：repo 裡的 example 是範本，
不是鏡像（09-05 實測 prod 33 筆 vs example 24 筆）。本 spec 要改的正是這份清單，改之前看不到現況、
改之後看不到差異，決策就無法從 repo 重新推導。

**Why this priority**: US1 的變更要能被審閱與回溯，這一條必須先完成。

**Independent Test**: 拿 repo 裡的那份與 prod 變數比對，結果一致；改一筆再比，差異看得出來。

**Acceptance Scenarios**:

1. **Given** prod 的來源清單，**When** 讀 repo，**Then** 能得知每一筆來源（名稱、型別、啟用與否）與 prod 一致。
2. **Given** 有人只改了 prod 變數、沒改 repo，**When** 執行既有的漂移檢查（或本 spec 落地的同等機制），
   **Then** 不一致會被報出來，而不是沉默。

---

### User Story 3 - 來源「會不會進池、進的是不是正題」上線前可評估、上線後可追蹤 (Priority: P2)

07-20 的六個來源上線後三週才看出沒進池，而且是人工追查才發現。使用者要：上線前就能看到候選來源
（新增的，或調整後的既有來源）的當期樣本會有幾篇進 digest 池、沒進的卡在哪一關、進的是不是正題；
上線後每週能從 log 讀出每個來源的實際進池篇數。

**Why this priority**: 沒有它，US1 成功或失敗都無法歸因到來源；但它本身不提高 L1。

**Independent Test**: 對一個已知會進池的來源（`交通安全教育`）與一個已知不會的來源跑評估，兩者結果要分得開。

**Acceptance Scenarios**:

1. **Given** 一個候選來源，**When** 執行上線前評估，**Then** 報出當期樣本在每一關（收集、新鮮度、相關性、分類、近似重複）
   剩下的篇數、最終落在匯流四類的篇數，並列出那些篇的標題供人工判讀正題與否。
2. **Given** 新來源已上線，**When** 週報執行，**Then** log 有逐來源的進池篇數，不必查資料庫就能判讀。

---

### Edge Cases

- **候選來源的當期樣本為 0 篇**：評估照樣輸出各關數字（全 0），不得因為空而略過輸出。
- **新來源變成最大來源**：L1 的定義不變（抽掉的是當週最大的那個），照算。
- **新來源的稿子與既有來源是同一則新聞**：近似重複會在 buffer 階段被擋，進池的只有一篇；
  評估與逐來源足跡都以去重後為準。
- **新來源的標題落在 `行人事故`／`路口安全`**：不進池。這是 07-20 的失敗形狀，評估要能直接看出來。
- **週報 runtime 逼近上限**：10-12 已是 9m05s，見 FR-006。
- **調整既有來源的 query 後，舊 query 收過的稿子**：已在庫的照舊，不回溯改分類；評估只看新 query 的當期樣本。
- **prod 變數與 repo 副本不一致**：以 prod 為準並報出差異，不得靜默覆寫任一邊。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 變更來源清單之前，MUST 先落地 `GNS-20261005-crb` 的一條修法（example 改成鏡像，或另存來源清單
  快照並納入漂移檢查），使 repo 能反映 prod 的來源清單現況。
- **FR-002**: 每個候選來源（新增，或調整 query／豁免後的既有來源）上線前 MUST 經過評估：以其當期樣本走真實的
  收集 → 新鮮度 → 相關性 → 分類流程（跑真實入口，不重寫邏輯），報出每一關剩下的篇數、最終落在匯流四類的篇數，
  並列出那些篇的標題供人工判讀正題與否。
- **FR-003**: 新增或調整的來源，其貢獻 MUST 以「進入 digest 池的篇數」計，不以收集篇數計。
- **FR-004**: 週報 log MUST 留下 digest 池的逐來源篇數，使每個新增或調整的來源的進池篇數不必查資料庫就能讀出。
- **FR-005**: MUST NOT 把 `行人事故`／`路口安全` 納入匯流（013 已排除：會把政策彙整變成事故彙整）。
- **FR-006**: 變更來源後，週報與 daily MUST 仍在憲章 IV 的單次上限內完成（以 10-13 起修訂後的條文為準）；
  上線前要估算新增耗時，上線後由週驗收的 runtime 比較追蹤。
- **FR-007**: 每個新增或調整的來源 MUST 可單獨回復（新增的停用；調整的還原成調整前的設定），回復後管線行為回到變更前的狀態。
- **FR-008**: 新來源帶來的每日篇數增量與其 embedding 成本增量 MUST 估算並記錄（本機 key 與 prod 同一把，
  評估時呼叫也計費）。
- **FR-009**: taxonomy 關鍵字 MUST NOT 變更，也不新增「來源強制指定類別」的機制；只採用照現行分類規則就會進池的來源。
  為來源加 `source_defaults` 對映、設相關性豁免、收窄既有來源的 query、停用全是雜訊的來源，都屬於來源設定，在範圍內。

### Key Entities

- **來源**：來源清單中的一筆（名稱、型別、URL、啟用與否、選用設定）。Google News 的不同 query 各算一個來源，
  即使背後的媒體重疊——這與 013 起 L1 的計算方式一致。
- **digest 池**：與 013 相同（某週內、屬於匯流四類、未被排除的文章）；本 spec 不改它的定義。
- **L1 指標**：匯流後的整池（`pool_all`，含低於品質下限者）抽掉當週最大來源後的篇數，對照 `trigger_count`（10）。
  與週報「最大來源」行、`replay_digest_pool.py` 的算法相同。
- **進池篇數**：某來源在某週進入 digest 池的篇數（去重後）。

## Success Criteria *(mandatory)*

**量測前提**：L1／L2 讀自週報 log 的「最大來源」行（週驗收 routine 每週判定）；逐來源進池篇數讀自 FR-004 的 log。
硬門檻只收實測。

### SC-001 承重（本 spec 的主要目標）

- **SC-001 L0 / Gate（上線前，離線）**：每個被採用的候選來源，FR-002 的評估中進入匯流四類、且人工判讀為正題的篇數 > 0。
  錨定：07-20 那六個來源若當時有這一關，「進不了池」在上線前就看得到，不必等三週；10-13 的 `天下交通` 豁免後
  會進池 17 篇、正題 0 篇，只看篇數會讓它過關。
- **SC-001 L1**：上線後連續 4 週，週報的 L1 全部通過（抽掉最大來源剩 ≥ 10）。
  錨定：上線前 8 週 5／8 過，最長連續 4 週（08-31～09-21），最低 6（10-12）。
- **SC-001 L2 / 理想**：連續 4 週最大來源佔比 ≤ 50%（013 的 L2）。錨定：013 上線以來只有 10-05 一週達到（47.4%）。

### SC-002 新來源真的進池

- **SC-002 L0 / Gate**：上線後 4 週內，每個新增或調整的來源至少有一週進池篇數 > 0；做不到的要回復（FR-007），或寫明保留理由。
- **SC-002 L1**：記下每個新來源從上線到第一次進池的週數（lag），作為下次補來源的依據。

### SC-003 runtime 與成本

- **SC-003（硬門檻）**：上線後週報與 daily 每次都在憲章 IV 的單次上限內完成（以修訂後的條文為準；修訂前是 10 分鐘）。
- 每日篇數增量與 embedding 成本增量要報出數字（不設門檻，是記錄）。

### SC-004 雜訊誠實計入

- 新來源帶進 digest 池的離題篇數與比例 MUST 報出（人工逐篇判讀，結果寫進驗收紀錄），不得以「現況也沒擋」略過。
  這是 `GNS-007`（政策 digest 離題雜訊）的可比較數字。

### 驗收時點

- **closeout**：新來源上線，且 SC-001 Gate、SC-003 通過，就收 PR。
- **closeout 之後**：SC-001 L1／L2 與 SC-002 由週驗收 routine 每週讀 log 追蹤；closeout 時 `GNS-008` 那一列移出，
  換成一列追這三項（含完成標準與停用判準）。`GNS-008` 的常設重開條件搬進新列，週驗收 routine 的常設檢查 (A)
  改指新列——重開條件不得隨 closeout 消失。

## Assumptions

- **L1 的定義與 013 相同**，好讓 `GNS-008` 觀測記錄前後可比；不另立新指標。
- **補幾個、補什麼 query 不在 spec 預設**：由 plan／research 依 FR-002 的評估結果決定。
- **匯流清單不動**（仍是 `路權政策`／`科技執法`／`交通工程`），`trigger_count`、`max_articles`、品質下限都不動。
- **只動 traffic 的政策來源**；FFXIV 不在範圍。
- **方向 A（比對窗＝本週＋上週）已上線**：上線後的 L1 以 A 之後的池為準；A 會讓池子略小（10-12 量到的影響最多 2～3 則新聞）。

## 已知限制（誠實標註）

- **Google News RSS 不能回溯**：上線前評估只能看當期樣本，看不到過去幾週的產量；lag 只能上線後量（SC-002 L1）。
- **n 小**：L1 的錨定只有 8 週；4 週的觀察期仍可能遇到量特別少的一週。
- **近似重複的互動**：新來源的稿子若與既有來源同則，去重後只算一篇；去重先擋哪一篇，會影響「算在哪個來源」。

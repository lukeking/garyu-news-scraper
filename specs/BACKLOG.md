**這份檔案是本 repo 的狀態記錄**——一個項目 ship 之後要從中移出的就是下面那張表

（在 spec 與 PR）。

**id 慣例**：`GNS-YYYYMMDD-xxx`——專案代碼、開條目那天、3 個 Crockford base32 小寫亂數字元。
格式、代碼登記與為什麼不用連號：`~/.agents/templates/BACKLOG.md` 與
`~/.agents/instructions/rules/output-conventions.md`「序列編號」一節。**id 由腳本產生，不要自己編**：

```bash
python3 ~/.agents/bin/backlog.py add specs/BACKLOG.md <項目> <觸發點> <完成標準>   # 印出新 id
python3 ~/.agents/bin/backlog.py remove specs/BACKLOG.md <id>                     # 移出整列與它的小節
```

寫完讀一次 diff。找 id 用 `grep -w`。離場的條目用 `git log -S "<id>" -p -- specs/BACKLOG.md` 整列撈回來。

後綴長度：3

**舊稱對照**：2026-09-21 之前的 commit、PR、memory 與程式註解裡寫的「BACKLOG #N」＝ `GNS-0NN`

**表裡只有還沒做完的條目，沒有狀態欄。** 在表裡＝還要做；做完就在完成它的那個 PR 裡整列移出

**單元那一半已經付掉了**（PR #114 的 JS harness，現有 25 個測試，與 Python 同在 CI 的

## GNS-009 桶分數門檻殺乾淨小桶（門檻是對「未過濾的桶」校準的）

**提出**: 2026-08-08，spec 012 量測 SC-004 時發現（**實測副產物，不是推測**）
**優先度**: 建議順序 GNS-009——不擋任何人，但它是**三個既有問題的共同結構根因**
**範圍**: 012 的 T016 明文把它排除在 012 範圍外，要另開 spec。

**問題**：`min_threshold` 是對**未經過濾的桶**校準的。相關性閘移除離題文章後，桶分數必然下降
（`score = Σquality × log(來源數+1) × log(天數+1)`，**三個因子同時縮小**），於是一個**乾淨但小**
的桶會跌破門檻、整桶不發布——連它的 on-topic 文章一起帶走。

**實測（spec 012，實測）**：`機車事故 · 中央社` 過濾後剩 2 篇乾淨事故文、分數 0.63，
`min_threshold: 1.5` → 不發布。012 的 4 筆 on-topic 損失裡有 **3 筆是這個原因**（另 1 筆才是規則漏抓）。
這正是 SC-004 卡在 L0 上不去 L1 的唯一原因——**不是 token 沒調好**。

**與 spec 010 是同一個結構問題**：010 的 道安政策 singleton 天花板 0.22 vs 門檻 1.0，
也是「內容沒問題，但量體撐不起分數」。010 用 digest（聚合）繞過去，沒有解掉門檻本身。

**已量測否決的兩條捷徑（別再走一次）**：

| 方案 | 實測結果 |
|---|---|
| (a) 全面降 `category_min_threshold` | 掃到 ≤1.0 時離題比例**爆回 100%**——髒桶跟著一起復活 |
| (b) 桶分數改用「過濾前」計算 | 離題 **100%**、SC-001 直接失守——該死的爛桶不再死 |

**核心難點**：同一個門檻同時殺乾淨小桶與髒桶，而**用分數分不開它們**——因為分數不含相關性資訊，
這恰好又是 GNS-007／機車事故那條線的同一個病根在另一個位置復發。需要比「降門檻」更聰明的東西
（例如把門檻改成對過濾後的桶重新校準、或讓乾淨度進入分數、或對小而乾淨的桶走 010 式聚合）。
**未評估，開 spec 時再比。**

### 界線

與 GNS-010（機車事故 require 表漏抓真事故，PR #97）：GNS-010 是「真事故根本沒進桶」，在閘；本項是「乾淨小桶跌破門檻」，在門檻。

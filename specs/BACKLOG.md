## CI gating（PR 自動跑測試）

**提出**: 2026-07-21
**狀態**: ✅ **L0＋L1 已完成**（PR #77 L0／#78 L1，2026-07-27）——`.github/workflows/tests.yml` 於 `pull_request` 跑 `pytest tests/unit`，`unit` 已是 ruleset 16977362 的 required check。**L2 刻意不做**（見階梯）。
**優先度**: **最高**——但使用者明示「不是現在」（07-27 已完成 L0/L1）
**依賴**: L2 需要「整合測試指向本機 Supabase」先完成（該前置已於 PR #79 完成，但 L2 仍刻意不納入）

**問題**：**這個 repo 完全沒有 CI。** 沒有任何 workflow 掛在 `pull_request` 上，
也沒有任何 workflow 跑 pytest。140 個測試（unit 127／integration 13）
**只在有人手動跑的時候才存在**。2026-07-21 的 PR #67～#70 全部零自動檢查就 merge。

**main 的現況**（用 rulesets API 查，**不是**舊的 branch protection 端點——那個會回 404 誤導）：

```
ruleset 16977362  main  enforcement=active
rules: deletion, non_fast_forward, pull_request
required_status_checks: []     ← 空的
```

保護已經在了（不能刪、不能 force push、必須走 PR），**只差 required check**。
所以這題不是「建立分支保護」，是「往既有 ruleset 加一個檢查」。

**為什麼優先度最高**：它是「把決策寫成機器會檢查的約束」這個機制的**前置**。
沒有 CI 的測試等於加了步驟的註解——寫一個「每日路徑零 AI」的測試，沒人跑的話，
下場跟那句說謊的 docstring 一樣。而且此專案的變更多由 AI 助理高速產出、
使用者 review 的常是散文摘要而非逐行 diff，**這種配置下自動閘門的價值比一般 solo project 更高**。

ROI 特別好：**測試已經寫好了，價值已建好只是沒被收割**，缺的只是一個 runner。

**階梯**：

| 階 | 內容 | 依賴 | 成本 | 狀態 |
|---|---|---|---|---|
| **L0** | `pull_request` 觸發 `pytest tests/unit`（127 個） | 無，隨時可做 | 約 1 分鐘/次 | ✅ PR #77 |
| L1 | 把 L0 加進 ruleset 16977362 的 `required_status_checks` | L0 | 設定變更 | ✅ PR #78 |
| L2 | 納入 `tests/integration` | ~~等 Supabase 隔離那條~~（已於 #2 完成） | — | ✗ 刻意不做（見 STATE） |

**L2 的陷阱，不可天真打開**：整合測試會寫正式 Supabase。直接開會分岔成兩條爛路——
不給憑證則測試 skip、拿到**假綠燈**（latent 失敗繼續躲著）；給憑證則**每個 PR 汙染正式資料庫**，
就是 2026-07-21 那件事乘以 N。

**一個必須一起想清楚的限制（使用者提出）**：
把決策寫成測試**並不能讓決策免於腐朽**。有人為了改核心邏輯順手調整測試時，
若測試沒記錄「什麼絕對不能動」，約束會無聲死掉——而且對方會真心認為自己在修一個過時的測試。

本 repo 已有現成反例：`test_filter_attaches_category_and_score` 在有憑證環境長期 fail，
處理方式是標成 latent 繞過，**一個已經爛在原地的測試**。

所以：測試贏過註解的地方**只有一個**，是讓違反的那一刻可見；它不會讓決策變永久，
沒有東西能做到那件事。決定會不會腐朽的不是媒介，是**那個東西有沒有記錄自己的重開條件**。
因此若要寫「決策型測試」，測試名稱與失敗訊息 MUST 帶上決策出處與重開條件，
讓對方必須**自覺推翻一個決策**而不是**修一個壞掉的測試**。
結構性補強只有 CODEOWNERS／path-scoped required review——不是防止刪除，
只是讓沉默的那條路變貴。

**與「正文抓取結案不做」不衝突**：那條結案的是抓**內文**合成摘要

**為什麼會這樣（使用者親述的設計沿革，2026-07-21）**：專案早期是每天爬完就丟 LLM 產分析，

**它不是「每日忘了跑分析」，是一個零 AI、約 1.7 秒/篇的預抓被歸類成了重度分析。**

## Buffer list 列模型重新設計（讓圖片在掃描時就能用）

**提出**: 2026-07-21，011 驗收時使用者實測發現
**優先度**: 未定——取決於圖片覆蓋率是否會成長

**問題**：011 的 US3 驗收情境 2 要求「具備圖片與可用摘要的文章，使用者**檢視列表**時視覺重量
高於僅有標題的文章」。實作把縮圖放進 `tr-detail`（預設隱藏的展開區），因此**在掃描視圖裡
有沒有圖對視覺重量的貢獻是零**。使用者原話：「沒辦法從收合狀態一眼看出哪一則是有圖的。」

US3 的另一半（`hot_topic_analyzed` 星號標記）有做到，圖片這條沒有。這是 011 的已知缺口，
不是新需求。

**為什麼不能用便宜的補法**：現行密集列是 `padding: 8px 6px` 的單行，高度約 30px。
塞得進去的縮圖小到看不出內容。加個「有圖」小圖示成本低，但它只告訴使用者圖存在、
沒讓使用者**用到**圖——掃描時有用的是看見圖的內容，而且每列加符號會提高密集列的視覺噪音。
真正的解法要動列的形狀，那就是列模型變更，不是樣式調整。

**✅ 資料封鎖已完全解除（2026-08-10）**：#3 已於 PR #81 補上缺口，滿週真實覆蓋率也已量到。
**現在可以判斷本題值不值得做了**——用 84.8%，不要用舊的 23–33%（那是缺口的產物，不是天花板）。

**覆蓋率**（E1 實測）：

| 期間 | 圖片覆蓋率 | 備註 |
|---|---|---|
| W20–W28（2026-07-21 量） | **0%** | 缺口期 |
| W29 | 33% | 缺口期，僅週一那批有圖 |
| W30 | 23% | 同上 |
| **08-03 ~ 08-10（滿週，191 篇）** | **84.8%** | PR #81 後的真實速率 |

**這個數字反轉了本題的前提**：原本寫「多數列沒有圖，任何以圖為主的版面都必須對『多數列無圖』
有交代」——**新資料下多數列有圖了**（85%），所以「以圖為主」的版面現在是可行的設計。
但**舊週仍是 0%，歷史資料不會回填**，所以列模型仍必須同時處理「整週無圖」的情形，
011 訂的「突顯手法不得依賴圖片」那條約束**不因此解除**——它現在保護的是舊週，不是多數列。

- ~~**多數列沒有圖，且舊週全部沒有。**~~ **前半已於 08-10 被推翻**（新週 84.8% 有圖），
  **後半仍成立且仍是本題的主要約束**：舊週是 0%，歷史資料不會回填。所以版面要面對的不是
  「多數列無圖」，而是**「有圖率在週與週之間從 0% 跳到 85%」**——同一個列模型要同時撐住兩端。
  這仍然是 011 把 US3 排 P3、並明訂「突顯手法不得依賴圖片」的原因，只是理由從「量太少」

## 評分核心純化與分離

**提出**: 2026-07-21，助理主動提出的重構建議
**優先度**: 建議順序 #4
**時機**: **下次要動 `src/analyzer.py` 時順手做最自然**，不建議現在專門開一題

**問題**：`src/analyzer.py` 裡「決定性的評分邏輯」與「會打外部服務的呼叫」住在同一個檔案。
`_call_gemini`、`analyze_hot_topic` 與 `score_topic_buckets`、`cluster_traffic_articles` 混在一起，
從模組結構看不出哪些函式是純的、哪些會產生成本與網路相依。

**現況比預期好很多**（2026-07-21 實測，這是重構而非重寫的理由）：評分路徑**幾乎全是純函數**——

```
normalise_title(title) -> frozenset                                    src/filter.py
compute_jaccard(set_a, set_b) -> float                                 src/filter.py
assign_category(title_tokens, taxonomy) -> str                         src/filter.py
compute_quality_score(article, category_keywords, config) -> float     src/filter.py
cluster_traffic_articles(articles, config) -> dict                     src/analyzer.py
score_topic_buckets(buckets, config) -> dict                           src/analyzer.py
select_hot_topics_with_novelty(buckets, scores, prior_reports, config) src/analyzer.py
select_digest_pool(articles, category, digest_cfg, excluded_links)     src/analyzer.py
```

**每一個都把 config 當參數注入、不讀全域狀態**，連新穎度閘要比對的 `prior_reports` 都是傳進去的。
同輸入必同輸出，本來就可重播。

**唯一的雜質是 `embed_dedup`**（呼叫 Gemini 算 embedding）。但 embedding **已經存進
`articles` 表**，改成接受預先算好的向量即可讓整條評分路徑 100% 純。

**為什麼值得做（依重要性）**：
1. **憲章 V 單一職責**——純運算與外部呼叫不該共處一個模組。
2. **讓核心能離線測**——目前測評分邏輯需要憑證與活資料，這正是整合測試會寫進正式庫的成因之一；
   純核心 + 凍結語料可完全離線跑，直接回饋 CI gating（建議順序 #1）。
3. **附帶效果**：分乾淨之後，「凍結語料 → 重播 → 觀察中間過程」幾乎是免費的。

**⚠️ 因果方向**：本項的正當理由是上面 1 與 2 的結構問題。學習產出是**副產品，不是理由**——
不可為了產生學習題材而擴大這項的範圍（見 memory `feedback_learning_integration_model`）。

**若要一併蒸餾學習產出，缺的三件事**：
- 純／不純分離（本項）
- 一份凍結的 fixture 語料（讓核心離線可跑）
- 中間過程的視覺化輸出——依 `learning-style` 這屬於**學習基礎建設，不得推遲到末期**

**已識別的學習線索**：這條評分路徑（正規化 → 分類 → 品質分數 → Jaccard 分群 → bucket 動能計分
→ 新穎度閘 → 選材）是 **Topic Detection and Tracking** 領域的一個實例。白話：「一串不斷流進來的
新聞，怎麼自動判斷哪些在講同一件事、哪件事是新出現的、哪件事已經報導過」。對應關係：
分群＝topic clustering、新穎度閘＝novelty detection / first story detection、跨週去重＝event tracking。
價值在於**已有能跑的系統可以反推理論**，不在於技術新穎。

## 桶分數門檻殺乾淨小桶（門檻是對「未過濾的桶」校準的）

**提出**: 2026-08-08，spec 012 量測 SC-004 時發現（**實測副產物，不是推測**）
**優先度**: 建議順序 #9——不擋任何人，但它是**三個既有問題的共同結構根因**
**狀態**: 待開 spec（012 的 T016 明文排除在 012 範圍外）

**問題**：`min_threshold` 是對**未經過濾的桶**校準的。相關性閘移除離題文章後，桶分數必然下降
（`score = Σquality × log(來源數+1) × log(天數+1)`，**三個因子同時縮小**），於是一個**乾淨但小**
的桶會跌破門檻、整桶不發布——連它的 on-topic 文章一起帶走。

**實測（spec 012，E1）**：`機車事故 · 中央社` 過濾後剩 2 篇乾淨事故文、分數 0.63，
`min_threshold: 1.5` → 不發布。012 的 4 筆 on-topic 損失裡有 **3 筆是這個原因**（另 1 筆才是規則漏抓）。
這正是 SC-004 卡在 L0 上不去 L1 的唯一原因——**不是 token 沒調好**。

**與 spec 010 是同一個結構問題**：010 的 道安政策 singleton 天花板 0.22 vs 門檻 1.0，
也是「內容沒問題，但量體撐不起分數」。010 用 digest（聚合）繞過去，沒有解掉門檻本身。

**已量測否決的兩條捷徑（別再走一次）**：

| 方案 | 實測結果 |
|---|---|
| (a) 全面降 `category_min_threshold` | 掃到 ≤1.0 時離題比例**爆回 100%**——髒桶跟著一起復活 |
| (b) 桶分數改用「過濾前」計算 | 離題 **100%**、SC-001 直接失守——該死的爛桶不再死 |

**核心難點**：同一個門檻同時殺乾淨小桶與髒桶，而**用分數分不開它們**——因為分數不含相關性資訊，
這恰好又是 #7／機車事故那條線的同一個病根在另一個位置復發。需要比「降門檻」更聰明的東西
（例如把門檻改成對過濾後的桶重新校準、或讓乾淨度進入分數、或對小而乾淨的桶走 010 式聚合）。
**未評估，開 spec 時再比。**

**結論不變但理由換了**：仍然用 YAML parse 比物件——不是因為偏移量不可預測

而且任何一端的編碼／EOL／尾端空白變動都會讓它假失敗。

**同日附帶處理**：`config/pipeline_config.yml` 是本 repo **唯一**還帶 CRLF 的檔（105/105 行），

該規則只在 git 自己 checkout／add 時套用，而 git 永不讀寫被忽略的檔。
其餘 gitignored config 是 LF 屬於**出身運氣**（多半複製自被追蹤的 `.example`），不是有東西在守。

**⚠️ 不要直接把「車禍」加回去。** 它是 T012 **刻意移除**的，`categories_traffic.yml`

**本週未造成損害，但理由不是閘做對了**：機車事故本週完全沒發布，原因是 **novelty gate**
（`bucket_9 score=16.935 prior=yes → suppress`、`bucket_34 → suppress`），不是相關性閘也不是門檻。
那 9 筆誤殺是各自獨立的單一事件（只有土城×2 同事件），依 012 實測「2 篇桶 ≈ 0.63 vs 門檻 1.5」，
就算沒被閘擋也幾乎確定進不了發布。**所以這是一個「還沒咬到人」的缺陷，不是正在流血的傷口**——
這也是它排 #10 而不是更前面的理由。

**⚠️ 這 9 筆是下限，不是全部**：近失詞掃描只抓得到**清單裡列出的詞**，一篇用完全不同詞彙

## 熱點分析杜撰來源沒有的事實（grounding 缺陷，08-14 新增）

**狀態**: ⏳ 待確認範圍。**證據等級 E3（judge 判讀）→ 需 E1 擴大取樣**。

**來源**: `gemini-3.6-flash → 3.7-flash` 模型汰換實驗
（`experiments/model-quality-3p6flash-vs-3p7flash/`，2026-08-14）的副產物。盲評 judge 在
**B3_道安政策** 桶（category pool，n=16）反覆點名：**兩個模型的 3 次生成都**捏造了來源文章 [7]
中不存在的關鍵事實——「新生禁行機車」與「事故率下降三成」，並據此展開 §一 因果分析。

**為什麼是缺陷、又為什麼不急**：
- 杜撰的事實**進了報告本文**（若該桶發布，讀者會讀到假事實）——正確性問題，非風格。
- 但**與模型無關**（3.6／3.7 皆然、各 3 次）→ 是 `analyze_hot_topic` 的 prompt／grounding 問題，
  **換模型救不了**。它也解釋了實驗中 **文本依據軸 ~3.1/5**（兩模型皆低）＝兩模型共同弱點。

**⚠️ 證據很薄**：**1 桶、1 週、N=3**。不知道是 B3 這批來源特有（[5][7][8] 是「駕艙機車禁行國道」
的異質內容，可能誘發模型把不同文章的事實混接），還是 `analyze_hot_topic` 的普遍傾向。
**動手前先擴大取樣**（多週多桶，量「報告本文出現來源查無的具體數字/禁令」的比率），
否則會對一個 B3-specific 的假象過度反應。

## 每日管線跳過 og 充實（圖片覆蓋率的真因）

**提出**: 2026-07-21
**狀態**: **等 2026-07-27 週一排程一起盤點**（使用者決定，不預先實作）
**優先度**: 待盤點後定；但它是上一題「列模型重新設計」的前置

**問題**：每日與每週跑的不是同一條管線。

| 執行者 | 流程 | og 充實 |
|---|---|---|
| `main.py`（每週一） | collect → filter → **analyze** → publish | ✅ |
| `scripts/traffic_buffer.py`（每日） | collect → filter → publish | ❌ **跳過 analyze** |

`enrich_articles`（GN 連結還原 + og:description/og:image 抓取）住在
`TrafficCategory.analyze()`，而每日 runner 從未呼叫它。`traffic_buffer.py` 只有一個 commit，
docstring 寫著「filter + **enrich**」但程式碼從來沒有 enrich 過——不是後來被移掉的迴歸，
是一開始就沒接上。

**實測證據**（按 `buffered_at` 分批，GN 來源，E1）：

| 批次 | GN 篇 | 已還原 | 有圖 |
|---|---|---|---|
| **07-13T01（週一）** | 20 | 20 | **18（90%）** |
| 07-14 ~ 07-19（每日 ×6） | 35 | **0** | **0** |
| **07-20T01（週一）** | 22 | 22 | **13（59%）** |
| 07-21T01（每日） | 45 | **0** | **0** |

有圖那批的 `image_url` 全是 publisher CDN（`img.ltn.com.tw`、`imgcdn.cna.com.tw`），
是真的 og:image；沒圖那批的 link 還停在 `news.google.com`，連還原都沒做。
GN 來源佔 traffic 全表 396/642 = **62%**，所以這個缺口影響的是多數文章。

**與「正文抓取結案不做」不衝突**：那條結案的是抓**內文**合成摘要
（被擋網域與缺 og:description 網域重疊 64% vs 5%）。這裡是 og: metadata，
既有實作、已在跑、已證明有效，是不同的東西。被擋網域的問題應該正是 07-20 只有 59%
而 07-13 有 90% 的原因之一。

**盤點時要確認的**：
- 90% vs 59% 落差很大而 n 僅 20/22。穩態速率未知——這是兩個點，不是一條線。
- 成本：throttle 0.4s／篇，45 篇約 18 秒加抓取時間。每日 run 目前約 100 秒，
  憲章 IV 的 10 分鐘上限應該很寬鬆，但**未實測**（E3）。
- 憲章 I（Pipeline Integrity）要求 stage 完整：每日跳過 analyze 是否本來就是刻意設計？
  `traffic_buffer.py` 的註解說「No AI calls」——若 analyze 未來會含 AI 呼叫，
  直接接上會破壞那個保證。需要確認 `enrich_articles` 是否真的零 AI（看起來是純 HTTP）。
- 補上後圖片覆蓋率實際會到多少，決定上一題值不值得做。

## Buffer list 列模型重新設計（讓圖片在掃描時就能用）

**提出**: 2026-07-21，011 驗收時使用者實測發現
**優先度**: 未定——取決於圖片覆蓋率是否會成長

**問題**：011 的 US3 驗收情境 2 要求「具備圖片與可用摘要的文章，使用者**檢視列表**時視覺重量
高於僅有標題的文章」。實作把縮圖放進 `tr-detail`（預設隱藏的展開區），因此**在掃描視圖裡
有沒有圖對視覺重量的貢獻是零**。使用者原話：「沒辦法從收合狀態一眼看出哪一則是有圖的。」

US3 的另一半（`hot_topic_analyzed` 星號標記）有做到，圖片這條沒有。這是 011 的已知缺口，
不是新需求。

**為什麼不能用便宜的補法**：現行密集列是 `padding: 8px 6px` 的單行，高度約 30px。
塞得進去的縮圖小到看不出內容。加個「有圖」小圖示成本低，但它只告訴使用者圖存在、
沒讓使用者**用到**圖——掃描時有用的是看見圖的內容，而且每列加符號會提高密集列的視覺噪音。
真正的解法要動列的形狀，那就是列模型變更，不是樣式調整。

**⚠️ 前置條件：先解決下方「每日管線跳過 og 充實」那一題，再回來看覆蓋率。**
目前的 23–33% 極可能是那個缺口的產物，不是天花板——在補上之前，用這個數字來判斷
本題值不值得做會是錯的。

**目前覆蓋率**（2026-07-21 全表實測）：

| 週次 | 圖片覆蓋率 |
|---|---|
| W20–W28 | **0%** |
| W29 | 33% |
| W30 | 23% |

- **多數列沒有圖，且舊週全部沒有。** 任何以圖為主的版面都必須對「多數列無圖」有交代，
  不能只設計有圖的那一小部分。這正是 011 把 US3 排 P3、並明訂「突顯手法不得依賴圖片」的原因。
  即使充實補齊，舊週仍是 0%——歷史資料不會回填。
- 既有的三種顯示狀態（hidden／collapsed／normal）與降級提示行都要在新列模型下維持，
  見 `specs/011-buffer-noise-triage/data-model.md` 的狀態轉換。

**注意**：這題與 RSS 無關，也與圖片資料品質無關。feed 已正確以 Media RSS
（`media:content` + `media:thumbnail`，命名空間已宣告）輸出圖片，且 **2026-07-21 使用者在
Feedly 實測確認有圖的項目正常顯示**。也就是說 `image_url` 的內容是可用的、呈現管道是通的——
唯一的問題是覆蓋率，以及網頁列表的掃描視圖用不到它。這條證據縮小了本題的範圍：
不需要重新檢討圖片抓取或資料品質。

## 整合測試指向本機 Supabase

**提出**: 2026-07-21，在實際造成正式資料汙染之後
**優先度**: 高於下方的前端測試框架——那項是**缺乏保護**，這項是會**主動造成損害**

**問題**：`tests/integration` 在 `.env` 有憑證時直接寫進**正式** Supabase 的 `articles` 表。
沒有任何防護把它擋下來，也沒有任何提示告訴執行者這件事正在發生。

**已發生的實害**：2026-07-21 為驗證 spec 011 而跑整合測試，插進 16 列測試資料
（`2025-W01-test` 等 week_id、`example.com` 連結）。汙染不只停在資料表——
`scripts/measure_source_uptake.py` 把它們納入統計，baseline 由 0.1954 位移到 0.1914，
每個來源倍率跟著偏，依此設定的 prod 變數 `SOURCE_UPTAKE_JSON` 整份是錯的，必須重設。
16 列已刪除，量測腳本已加 ISO week_id 過濾作為第二道防線——**但那只擋統計汙染，
擋不住資料被寫進去**。

**已知可用資源**：本機 Docker 已常駐一套 Supabase（容器 `supabase_*_backend`），
API `http://localhost:54321`、Postgres `localhost:54322`，金鑰由 `supabase status` 取得。
所以不需要新建基礎設施，只需要讓測試指過去。

**範圍草稿**（開 spec 時再確認）：
- conftest fixture：整合測試啟動時強制覆寫連線設定指向本機，**並在指向正式環境時直接 fail**
  而非放行。預設要安全，不能靠執行者記得。
- schema 建立／清理：本機實例是跨專案共用的，需要確認 `articles` 等表的建立方式。
- 唯讀診斷腳本**不在此範圍**——那些指向正式環境是正確且必要的，本 session 大量使用未造成影響。
  界線在「寫入」，不在「連線」。
- 順帶處理 `test_traffic_buffer::test_filter_attaches_category_and_score`：
  它在有憑證環境會 fail，長期被 skip 蓋住，實質上是同一個根因的徵兆。

## 前端測試框架（Storybook / E2E）

**提出**: 2026-07-21，從 011-buffer-noise-triage 的 Constitution Check 帶出
**優先度**: 低——「沒事幹的時候可以來實作」

**問題**：repo 的測試基礎建設全在 Python 端（`pytest`，`tests/unit` + `tests/integration`）。
JS 端**零測試**——`pages/shared/app.js`（約 510 行，含全部列表渲染、分組收合、
dismiss 狀態）與 `workers/api/src/index.js`（約 363 行，含全部端點與篩選邏輯）
都只能靠手動點擊驗證。

**觸發此項的具體事件**：011 的主要改動落在 JS 端，plan 階段只能在 Complexity Tracking
誠實記下「這是測試缺口，不假裝已覆蓋」，驗收改依賴 `quickstart.md` 的手動清單。
當時**刻意不順手引入框架**——那是未被要求的基礎建設，違反 YAGNI，也會讓 011 的
改動範圍失焦。但缺口是真的，且會隨每個前端 feature 累積。

**範圍草稿**（開 spec 時再確認）：
- Storybook 或等價工具：讓列表的各種狀態（空週、零圖片舊週、全部降級、全部收起、
  無摘要）能獨立呈現而不必造真實資料。這幾個狀態目前只能靠找到「剛好長那樣」的週次來驗。
- E2E：涵蓋 quickstart 裡那份手動驗收清單，特別是跨週次切換後的狀態行為
  （降級展開不持久化、來源收起要持久化——兩者相反，正是容易寫錯的地方）。
- Worker 端：純函式的契約測試（`normalizeRow`、篩選、以及 011 新增的雜訊推導）。

**注意事項**：
- Cloudflare Pages 前端無建置步驟（`pages/` 是手寫 HTML/CSS/JS 直接部署）。
  引入需要 bundler 的工具會改變部署模型——這是這項的主要成本，不是寫測試本身。
- 憲章 IV（Free Tier Discipline）：CI 若跑 E2E 需計入 Actions 每月 2000 分鐘額度。

# Research: 018 週報發布前審核

2026-11-07。每一節：決定、理由、考慮過的替代。查證日期都是 2026-11-07，價格與功能出自 `aistudio.google.com/docs/…`
（`ai.google.dev/gemini-api/docs/…` 會跳轉過去），核對方式同 PR `#201`：curl 抓原始 HTML、自己抽文字。

## R1 審稿模型

- **決定**：預設 `gemini-4-argon`，由新的 GitHub 變數 `GEMINI_REVIEW_MODEL_NAME` 指定。沒設定，或與 `GEMINI_MODEL_NAME` 相同時，
  不跑審稿，狀態記成「未審」並寫明原因（FR-007、FR-012）。上 prod 前用重播確認它過得了 SC-002 的 Gate；過不了就換候選再測一次。
- **理由**：
  - Luke 裁示用同一家廠商的另一個模型，不新增憑證。
  - argon 是 GA（模型頁 Versions：Stable `gemini-4-argon`），Capabilities 有 Structured outputs（審稿要回 JSON）。
  - 10-19 評比裡 argon 生成的報告每份引證 12.6 處，3.8 是 4.1 處（`experiments/model-quality-3p8flash-vs-argon/README.md`）。這是推論的佐證：它比較會對照來源，不是審稿能力的實測。
  - 價格（pricing 頁「Gemini 4 Argon」，每百萬 token）：到 2026-11-30 輸入 $2、輸出 $10；2026-12-01 起 $4、$20。量級見 R9。
- **替代**：
  - `gemini-2.5-pro`：較舊，留作 argon 過不了 Gate 時的第二個候選。
  - `gemini-3.1-pro-preview`：preview，不用在每週排程上。
  - 另一家廠商：Luke 裁示不用。

## R2 審與修合成一次呼叫，修稿由程式套用

- **決定**：審稿呼叫回一份 JSON（`contracts/review-output.md`），每條發現附**原句**（逐字取自報告）和**替換文字**（刪除就給空字串）。
  程式只套用中、高嚴重度的那幾條；原句在報告裡必須剛好出現一次才套，否則那一條不套、記原因。每條套完都跑一次 R5 的機械檢查，
  沒過的那一條退回，其餘照套。全部套完再對整份跑一次檢查；整份沒過，就改發原稿，狀態記「修稿未採用」。
- **理由**：
  - FR-010 要求「只改被點出的段落」。由程式做逐字替換，這條是機械保證；讓模型重寫整份就只能事後比對。
  - 一份報告只多一次呼叫，時間與費用都是另開修稿呼叫的一半。
  - 退回的粒度是單條，一條壞的替換不會連累其他修正。
  - spec 的「審一次、修一次」仍然成立：審是那一次呼叫，修是套用那一步，沒有第二輪。
- **替代**：
  - 另開一次修稿呼叫、讓模型重寫整份：沒被點出的段落可能被動到，費用與時間加倍。
  - 生成模型自己修：它就是犯錯的那個模型，而且同樣得重寫整份。
- **邊界**：要搬動結構的發現（例如偏頗類「刪掉論據」）可能沒辦法用一句替換修好。審稿可以不給替換，那一條就照記、不套，
  狀態記成部分套用。

## R3 生成指令怎麼改（FR-001～FR-005）

| 錯型 | 彙整（`DIGEST_*`） | 三軸（`HOT_TOPIC_*`） |
|---|---|---|
| 事件互相獨立的宣告 | system prompt 與 template 拿掉「各事件互相獨立」「這些是多個互相獨立的事件」，改成：不得自行推論事件間的因果、趨勢或風向，來源明文寫出的關聯照寫並標 ID | 沒有這句，不用改 |
| 報導日當事件日 | 清單的「日期：」改成「報導日：」；指令：寫時間時標「報導日」，除非來源明文寫出事件日 | 清單沒有日期，FR-002 不適用 |
| 計數交給模型 | 拿掉「本期共幾個獨立事件」；`### 本期概覽` 第一行由程式寫「本期收錄 N 篇報導，其中 M 篇只有標題」，模型只寫涵蓋哪些面向 | 「交織度分布 __篇」是模型分類後的計數，不是數清單；照留，由審稿查 |
| 只有標題的報導 | 不放進給模型的清單。編號接在有摘要的報導之後，由程式在文末加 `### 僅標題` 一節，照原標題逐行列出、附 ID（R4） | 照留在清單，摘要欄寫「（僅標題）」；指令要求引用時標「僅標題」，由審稿查 |
| 數字的範圍、因果 | 加一條：數字照來源寫範圍、期間與基準，不加來源沒有的範圍詞，統計定義的改變不寫成因果 | 同一條加進 C 軸指令 |

## R4 「只有標題」怎麼判定

- **決定**：摘要正規化（去空白與標點、全形轉半形）之後，符合以下任一條就算只有標題：空字串；與正規化的標題相同；被標題包含；
  扣掉標題之後剩不到 20 字。20 這個數字要校準：重建 10-19、10-26、11-02 三份的輸入，判出的篇數拿來對評論說的「每份 6–11 篇」，
  逐篇看邊界上的那幾篇，再定案（tasks 第一批）。
- **理由**：Google News 的 RSS 常把標題當摘要（`GNS-20261005-24s` 那批「只有標題」）；空白不是唯一的形狀。
- **替代**：只認空字串會漏掉「摘要＝標題」那種；用字數絕對門檻（摘要 < N 字）會誤殺短但真實的摘要。

## R5 機械檢查（修稿套用時，以及 SC-001／SC-003 的量測）

純函式，同一套給週報與重播共用：
- 各節標題都在（彙整：本期概覽、分節彙整、待追蹤、僅標題；三軸：一、二、三）。
- 報告裡每個 `[n]` 都在清單範圍內。
- 替換文字裡的數字，都要在原句或清單的標題、摘要裡出現過（擋「修出新數字」）。
- 只有標題的報導 ID 沒有出現在 `### 分節彙整`（SC-001）。
- `### 本期概覽` 沒有「共 N 起／個事件」這類模型自數的計數（SC-001）。
- 沒有「互相獨立」「無直接因果」「各自獨立」這類宣告（SC-001；詞表放在測試，對已發布原稿要找得到，證明檢查會咬）。
- 時間：清單日期以外的日期出現時，前後要有「報導」字樣，或原文摘要裡找得到那個日期（SC-001 的「沒標報導日」；啟發式，命中的逐條由 main 看）。

## R6 審稿標準與錨點

- **決定**：錨點寫成結構化資料（id、類別＝寫錯／偏頗、嚴重度、適用模板、原句、錯在哪），放在 `src/report_review.py`；
  prompt 由函式組裝，可以指定排除哪些 id（SC-002 留一測試：測某個錨點時，標準裡不放它）。
- 寫錯類：`s3h` 節的 5 個已驗證錨點。
- 偏頗類：main 從評論的待查清單（`s3h` 節「評論提出、main 沒有逐條對過的」）拿重建的報導清單與報告原文核對，成立的才收，至少 2 個。
- 三軸：用 11-06 同一套做法（headless `claude -p`，不給工具，扮資深新聞編輯）評幾份已發布的三軸報告，main 逐條核對，
  成立的收進錨點。只是取得錨點，不是 prod 的審稿者；prod 審稿照 R1 用 Gemini。
- 嚴重度三級，每級至少 2 個實例；分級的定義用「讀者會不會因此相信一件來源沒說的事」錨定：
  高＝會（例：統計定義寫成「造成 7 死」）、中＝範圍或時間讀錯但事件本身對（例：「全國」、報導日當事件日）、低＝措辭不精準但不致誤讀。
- **替代**：標準寫成形容詞分級（「嚴重」「一般」）——不錨定的話，每次呼叫重抽一個標準（`review-loop-bounds`「尺度」）。

## R7 審核紀錄存哪裡

- **決定**：Supabase 新表 `hot_topic_report_reviews`（`supabase_migrations/006_report_reviews.sql`），以 `(week_start_date, topic_label)`
  為唯一鍵 upsert，跟 `hot_topic_reports` 同一把鍵；由 `src/storage.py` 寫。prod 套用照現行做法，在 dashboard 手動貼；
  `scripts/setup_test_db.sh` 加上 006。
- **理由**：要長期查得到（FR-014），也要能拿來校準標準；artifact 只留 90 天。
  同一把鍵讓同一週重跑時覆寫成同一份，符合憲章 III。
- **替代**：
  - 在 `hot_topic_reports` 加 JSON 欄：混了發布資料與審核資料，Worker API 會把它一起讀出去。
  - Actions artifact：只留 90 天，也不能查詢。

## R8 週驗收怎麼看到

- 週報 log 每份報告印一行 `[審稿]` 摘要（格式是契約，`contracts/summary-line.md`，用測試鎖住）。
- `routines/weekly-verify/PROMPT.md` 加一節：從 log 逐字取出 `[審稿]` 行寫進報告，「未審」「修稿未採用」列出原因；
  一行都找不到時寫成「找不到審稿摘要」（沒訊號＝沒跑）。這個檔在 `.github/cold-review-paths` 裡，該 PR 要 cold review。

## R9 時間與費用（推論，重播後用實測更新）

- **費用**：一次審稿的輸入約 1.2 萬 token（清單最多 25 篇 × 400 字、報告約 2,400 字、標準約 3,000 字），輸出含 thinking 約 2,000 token。
  argon 每次約 US$0.044（11-30 前）或 US$0.088（12-01 起）。一週 3 份 × 4.35 週，每月約 US$0.6–1.2；加上現有的 US$0.80–1.60，
  仍遠低於 NT$300（約 US$9）的上限。
- **時間**：argon 10-19 生成一份熱點平均 21.4 秒；審稿輸出較短，估每份 20–40 秒，一週多 1–2 分鐘。
  11-02 週報 14.3 分鐘，估計落在 16 分鐘左右，低於 SC-004 的 20 分鐘那一階。
- **重播本身**：三份彙整重生成約 US$0.04；審稿 3 份加上留一測試 7 次，約 US$0.5。照 Luke 11-07 的話，可以拿已發布的報告測，
  花的是同一把 prod key、同一個月上限。

## R10 SC-002 第三階「誤報少」的門檻

- **決定**：每份報告被點出的發現裡，main 拿來源核對後成立的占一半以上。
- **理由**：審核摘要每週由 Luke 讀；誤報超過一半時，摘要是雜訊多於訊號，讀的人會開始略過它。
  這一階綁的是「摘要值不值得讀」這個場景，數字是那個場景的界線，不是借來的。
- **替代**：沿用 11-06 評論的成立率——那次只核對了 20 條裡的 5 條，沒有完整的成立率可以當基準。

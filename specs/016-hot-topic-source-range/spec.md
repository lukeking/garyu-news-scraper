# Feature Specification: 熱點報告標示來源涵蓋的日期區間

**Feature Branch**: `016-hot-topic-source-range`  
**Created**: 2026-11-02  
**Status**: Draft  
**Input**: BACKLOG `GNS-20261031-005`（交通頁的週報熱點掛在產生那週，內容卻是上一週的 buffer，跟同頁下方的文章差一週）。
Luke 2026-10-31 提出；2026-11-02 從三個候選（改標籤／只改呈現／只補標示）裡選「只補標示」。

## 背景：為什麼同一頁的報告和文章對不上

Luke 10-31 的原話：「traffic daily buffer 和週報產生週期跟 UI 呈現已經脫鉤，我打開介面看到的週報熱點分析是從上禮拜的
buffer 來的，但下方的 daily buffer 卻都是這週的。」

- 交通頁每個週次頁面，上方是掛在這一週的熱點報告，下方是這一週收集的文章。
- 報告在每週一產生，掛在產生那一週；它分析的是之前累積、還沒被分析過的文章，以上一週收集的為主，最舊可到 8 週前。
- 所以讀者在同一個頁面上，會以為報告講的就是下方那批文章，其實大多不是。

**2026-11-02 prod 唯讀量測**（55 份報告，不含一筆測試殘留）：

- 52 份的來源橫跨不只一個收集週。
- 每份報告「來源最多的那個收集週」：34 份是上一週，2 份是報告掛的那週，19 份是 2～7 週前。
- 彙整型報告的來源發布日期往回涵蓋近一個月（例：11-02 那份是 09-29～11-01）。

所以「報告屬於哪一週」沒有唯一的答案：把報告搬到任何一週都只是挑一週，不會更準。Luke 選的做法是報告不搬，
把它實際涵蓋的時間寫出來。

## Clarifications

### Session 2026-11-02

- Q: 卡片上的涵蓋區間顯示什麼——發布日期、收集週次，還是兩者？ → A: 只顯示發布日期（例「新聞發布 09-29～11-01」），不顯示收集週次。
- Q: 文章列 ★ 的提示寫「已納入本週熱點報告」，但收錄它的報告大多掛在後面的週次；要不要一併處理？ → A: 一併改。
  拿掉「本週」，或寫出收錄它的報告所在的週次；用哪一種跟畫面一起簽核。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 讀者看得出報告講的是哪段時間的新聞 (Priority: P1)

讀者打開交通頁的某個週次，看到一份熱點報告。卡片上寫著這份報告的來源涵蓋哪段時間，讀者不用比對下方的文章，
就知道報告講的不是（或不只是）這一週收集的那批。

**Why this priority**: 這就是 `GNS-20261031-005` 的核心——防止讀者把報告和同頁的文章當成同一批。

**Independent Test**: 打開任一有報告的週次頁面，每張報告卡片都看得到涵蓋區間；把區間和卡片列出的焦點事件逐篇的日期對照，
最早與最晚都對得上。

**Acceptance Scenarios**:

1. **Given** 2026-W45 的頁面（11-02 產生的兩份報告），**When** 讀者看報告卡片，**Then** 每張卡片都寫出來源涵蓋的區間，
   例如彙整報告顯示的區間從 09-29 前後到 11-01 前後，而不是只有 W45。
2. **Given** 一份來源全部在同一天的報告，**When** 讀者看卡片，**Then** 區間顯示成單一日期，不是「同一天～同一天」。
3. **Given** 一份來源跨好幾週的一般報告（例：11-02 的「機車事故 · 中時」，來源收集週從 W37 到 W44），
   **When** 讀者看卡片，**Then** 涵蓋區間把最早那篇也算進去，不只顯示來源最多的那一週。
4. **Given** 某個週次頁面上一篇帶 ★ 的文章（它被後面某一週的報告收錄），**When** 讀者看 ★ 的提示，
   **Then** 提示不再說它被納入「本週」的報告。

---

### User Story 2 - 已經分享出去的連結照樣打開原本那份報告 (Priority: P1)

有人之前把某份報告的連結（指到某個週次與某張卡片）分享到 LINE。改版之後點同一個連結，打開的還是那一週、
捲到的還是那張卡片。

**Why this priority**: 「只補標示」被選中的理由之一就是不搬報告、不破壞已分享的連結；這條沒守住，這個做法就失去它相對其他候選的優勢。

**Independent Test**: 改版前後，對每一份報告用同樣的分享連結打開，比對落在哪個週次頁面、捲到哪張卡片。

**Acceptance Scenarios**:

1. **Given** 改版前產生的任一份報告的分享連結，**When** 改版後打開，**Then** 頁面停在原本的週次，並捲到同一張卡片。
2. **Given** 改版後分享的新連結，**When** 打開，**Then** 連結的格式和改版前相同。

---

### User Story 3 - 之後每份新報告自動帶上區間 (Priority: P2)

上線之後的每一次週報，新產生的報告不用任何人工步驟就有涵蓋區間。

**Why this priority**: 只修既有的報告，下週就會再出現沒有標示的卡片。

**Independent Test**: 上線後第一次週報跑完，打開那一週的頁面，新報告的卡片都有區間，且和焦點事件的日期對得上。

**Acceptance Scenarios**:

1. **Given** 上線後的第一次週報，**When** 它產生一般報告與彙整報告，**Then** 兩種報告都帶有涵蓋區間。
2. **Given** 某份新報告的來源全部沒有發布日期，**When** 頁面顯示它，**Then** 卡片不顯示錯的區間（見 Edge Cases），也不讓頁面壞掉。

---

### Edge Cases

- 焦點事件裡有一篇在資料裡找不到（2026-11-02 量到 602 條來源連結裡有 3 條找不到）：區間只用找得到的那些算，
  不因為一篇找不到就整張卡片不顯示。
- 一份報告的焦點事件全部找不到或全部沒有發布日期：卡片不顯示區間，其餘照常；不顯示「未知～未知」這類字樣。
- 發布日期比收集日期早很多（RSS 裡的舊文章）：區間照實顯示發布日期，不截斷。
- prod 裡有一份 2025-W02 的測試殘留報告（`酒駕-integration-test`，來源 0 篇找得到）：沒有任何週次頁面會顯示它，
  本 spec 不處理，但回填時不能因為它失敗。
- 跨年：區間的兩端在不同年份時，讀者仍能看懂（例如年份要不要寫出來，在設計畫面時決定）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 交通頁每一張熱點報告卡片 MUST 顯示該報告來源涵蓋的日期區間，計算對象是卡片列出的焦點事件
  （也就是送進分析的那批來源）。
- **FR-002**: 區間的兩端 MUST 是焦點事件裡最早與最晚的發布日期，以台灣時間的日期計；找不到或沒有日期的來源不計入。
- **FR-003**: 卡片上顯示的 MUST 是來源的發布日期區間（例「新聞發布 09-29～11-01」），不顯示收集週次。
- **FR-004**: 報告掛在哪一個週次 MUST 維持不變；已分享出去的報告連結 MUST 仍打開同一個週次、捲到同一張卡片。
- **FR-005**: 既有的報告 MUST 一次補齊涵蓋區間，補完之後所有能算出區間的卡片都顯示得出來。
- **FR-006**: 之後每一次週報產生的報告（一般與彙整兩種）MUST 自動帶有涵蓋區間，不需要人工步驟。
- **FR-007**: 文章列上 ★（已收錄進某份熱點報告）的提示 MUST 不再說「本週」：改成不指涉週次的說法，或寫出收錄它的報告
  所在的週次；用哪一種跟 FR-008 的畫面一起簽核。
- **FR-008**: 卡片上新增的標示 MUST 在亮色與暗色兩個主題下都讀得清楚；實作前先以兩個主題的實際畫面給 Luke 簽核。
- **FR-009**: FFXIV 頁面 MUST 不受影響（它沒有熱點報告區塊）。

### Key Entities

- **熱點報告**：每週一產生，掛在產生那一週；有一組焦點事件（送進分析的來源），新增「來源涵蓋的日期區間」。
- **來源文章**：有發布日期與收集週次；同一篇文章只屬於一個收集週。
- **分享連結**：指到某個週次與某張報告卡片；本 spec 不改它的格式與解析方式。

## Success Criteria *(mandatory)*

### SC-001 每張卡片都有區間（本 spec 的主要目標，實測）

上線後打開所有有報告的週次頁面：能算出區間的報告 100% 顯示區間；算不出區間的（來源全部找不到或沒有日期）不顯示、
頁面不壞。量法：逐份列出顯示的區間，與「焦點事件逐篇的發布日期」另外算出的最早／最晚比對，55 份全對。

### SC-002 分享連結不變（硬門檻，實測）

改版前後，55 份報告各自的分享連結落在同一個週次、捲到同一張卡片：55／55。

### SC-003 新報告自動帶區間（實測）

上線後第一次週報產生的每一份報告都有區間，且通過 SC-001 的比對。驗收時點是上線後第一個週一的週報。

### SC-004 兩個主題都讀得清楚（簽核）

實作前，Luke 看過亮色與暗色兩個主題的實際畫面並簽核；上線後的畫面與簽核的一致。

### SC-005 ★ 的提示不再說「本週」（實測）

上線後抽一個有 ★ 的週次頁面，★ 的提示文字是簽核過的那一種，且不含「本週」。

## Assumptions

- 報告不搬週次、分享連結不變。Checked: Luke 2026-11-02 選了「只補標示」，該選項的說明寫「報告留在原本的週次……已分享的連結不受影響」。
- 區間用卡片列出的焦點事件算，不用一般報告的整個 bucket 算。Unchecked: Luke 沒有指定；選這組是因為讀者看得到的就是這幾篇。
  若錯：一般報告的區間會比整個 bucket 窄，與現有的「最新來源日期」（用整個 bucket 算）對不起來。
- 焦點事件幾乎都找得到對應的文章。Checked: 2026-11-02 prod 唯讀查詢，602 條來源連結找到 599 條。
- 已分析過的來源文章不會被清掉，所以之後重算區間仍找得到它們。Checked: `src/storage.py` 的 `expire_buffer_articles`
  只刪 `hot_topic_analyzed=FALSE` 的過期列。
- 只有交通頁有熱點報告區塊。Checked: `pages/shared/app.js` 的 `loadWeek` 只在 `C.contentType === 'traffic'` 時呼叫 `renderHotTopics`。
- 卡片上「N 篇來源」的數字與焦點事件的篇數不一致（一般報告的 N 是整個 bucket，焦點事件最多 10 篇），本 spec 不處理。
  Checked: `scripts/traffic_weekly_analysis.py` 寫入 `source_article_count = len(bucket_articles)`，`src/analyzer.py` 的
  `analyze_hot_topic` 只取前 10 篇。Unchecked 的是讀者會不會因此困惑；若會，另開 BACKLOG。
- 發布日期以台灣時間的日期顯示。Unchecked: 沒有查過 DB 裡發布時間存的時區格式是否一致；若不一致，區間兩端可能差一天。

# Contract: 不發布的週報執行

讀者是觸發它的維護者、讀它紀錄的人與 routine。名字（環境變數、模式、檔名）是提案（未定），tasks 定案後回來改這份；行為是已定的（spec FR-001～FR-010、research D1～D5）。

## 入口

- 一個只能手動觸發的 workflow（提案的檔名：`.github/workflows/weekly-dry-run.yml`），沒有排程。
- 一個必填的輸入：級別。
  - 第一級（提案的值：`input`）：收集、過濾、充實、選出入選；不呼叫 LLM。
  - 第二級（提案的值：`full`）：第一級的全部，加分析、發布前檢查、術語收錄；不寫入、不發布。
- 可以選任一個分支執行；跑的是那個分支的程式。
- 跟 `weekly.yml` 共用的準備步驟（寫設定檔、裝 Python、裝相依）逐步相同，由 `tests/unit/test_workflow_parity.py` 守。
- 沒有部署步驟，也沒有「驗證本週資料可由資料庫讀取」那一步（它驗的是剛寫進去的資料）。

## 執行模式

- 程式從一個環境變數讀模式（提案的名字：`GARYU_RUN_MODE`）；沒設、或設成不認得的值時的行為：
  - 沒設：正式模式。正式排程的 workflow 不設這個變數，行為跟加入這個功能之前相同。
  - 不認得的值：直接失敗、不往下跑（提案，未定）。不退回正式模式的理由：拼錯一個字不能變成一次正式寫入。
- 每個寫入函式自己檢查模式。不發布時不呼叫資料庫，印一行，回傳 0。

## 執行紀錄裡的固定行

這幾行有讀者（維護者、之後的 routine），格式用測試鎖住。文字是提案：

| 什麼時候 | 行 |
|---|---|
| 每支程式開頭 | `[不發布] 第一級：只到入選，不呼叫 LLM` 或 `[不發布] 第二級：呼叫 LLM，不寫入、不發布` |
| 每一次被略過的寫入 | `[不發布] 略過 <寫入函式的名字>：<N> 筆` |
| 第一級停下的地方 | `[不發布] 第一級在 <階段> 之前停下` |
| 交通分析疊上這次收集的清單 | `[不發布] 分析的輸入：buffer <N> 篇，加上這次收集的 <M> 篇（其中 <K> 篇 buffer 裡已經有）` |
| 第二級結束 | `[不發布] LLM 呼叫 <N> 次` |
| 術語收錄 | `[不發布] 術語收錄：會寫入 <N> 條，沒有寫入`，後面逐條列出 |

正式模式下這些行都不出現。

## 產物

| 產物 | 哪一級 | 內容 |
|---|---|---|
| FFXIV 候選池（沿用現有的 `ffxiv-pool`） | 兩級 | 整個候選池與入選的篇數 |
| 交通這次收集過濾後的清單 | 兩級 | 每個來源的收集數、過濾後數、清單 |
| 熱點與彙整池的組成 | 兩級 | 選出的 bucket、彙整池的篇數與來源分布 |
| 分析輸出 | 第二級 | 每一份三軸報告、彙整報告、FFXIV 逐篇分析的全文，發布前檢查的結果 |
| 術語收錄的結果 | 第二級 | 會寫入的條目 |

產物之後可以拿來重播。這個 repo 是公開的，產物外人讀得到（已定可以）。

## 不變的東西

觸發前後，下面五個計數相同（SC-001）：報告數、buffer 筆數、彙整池未分析筆數、兩個站的最後部署時間、術語庫的條目數。
不發布的執行成功結束不會連帶觸發 `auto-kb.yml`（它只認週報 workflow 的名字）。

# Feature Specification: 分層驗收——改動照驗收範圍分片，各自發 PR、各自驗收

**Feature Branch**: `020-layered-acceptance`  
**Created**: 2026-11-15  
**Status**: Draft  
**Input**: BACKLOG `GNS-20261114-bh8`（`specs/BACKLOG.md` 的同名小節；已定與未定都以那一節為準）。改動照驗收範圍分片、一片一個 PR 各自驗收，
能用不發布的執行驗的不等排程的週報；範圍只改這個專案。spec 自己照同一個原則分片出貨，第一片是正式執行環境上不發布的跑法。

## 背景

**驗收條件的寫法把排程變成了所有事情的時鐘。** 2026-11-14 數 `6b0d0dc` 的 `specs/`、`routines/`、`docs/`、`.specify/`：「連兩週」23 處、「第一份週報」12 處、
「週報後」13 處。結果是一個改動整包等下一次週一的排程：`#218` 整包停到 11-23 週報之後，其實只有「prod 設變數後讀週報」那一片要等；
11-13 手上的五條待辦全卡在 11-16 週報。憲章沒有把排程當權威（排程住在 `.github/workflows/`，手動觸發是正當入口），把它變成權威的是驗收條件的寫法。

**現在沒有不留痕跡的跑法。** 手動觸發現有的週報流程會做跟排程一樣的事：寫報告、消耗彙整池、讓 buffer 過期、部署兩個站、連帶觸發術語收錄。
所以「想提早看結果」等於「提早發布一次」，沒有人會這樣驗。

**輸入要在正式執行環境驗。** 抓不抓得到跟執行環境的 IP 有關（同一批來源，本機拿得到、正式環境拿不到的例子記在 BACKLOG 小節的「結構事實」），
本機的執行只驗得到輸出。

## User Scenarios & Testing *(mandatory)*

四個 story 各是一片：有自己的驗法、自己的 PR。第一片的先後已定（2026-11-14）；其餘三片的先後是提案（未定），相依只有一條：第四片要用第一片的跑法。

### User Story 1 - 在正式執行環境跑一次不發布的週報 (Priority: P1)

維護者想確認一個改動的輸入與輸出對不對：在正式執行環境手動觸發一次不發布的週報流程，讀它留下的紀錄與產物，
不必等週一的排程，也不會留下任何對外可見或影響下一次執行的痕跡。跑法分兩級：第一級不呼叫 LLM，只跑到入選；第二級呼叫 LLM，但不寫入、不發布。

**Why this priority**: 已定排第一（2026-11-14）。`#218` 的接線卡在它；其他改動的「輸入」「輸出」兩種驗收也都以它為前提。

**Independent Test**: 兩級各觸發一次，讀執行紀錄與產物；觸發前後各取一次正式資料的計數（報告數、buffer 筆數、彙整池未分析筆數、兩個站的最後部署時間、
術語收錄流程的執行次數），前後相同。

**Acceptance Scenarios**:

1. **Given** 一個還沒 merge 的版本，**When** 維護者觸發第一級，**Then** 執行跑完收集、過濾與入選後停止，紀錄裡每個類別的收集數、過濾後數與入選清單都讀得到，LLM 呼叫 0 次。
2. **Given** 同一個版本，**When** 維護者觸發第二級，**Then** 分析的輸出全文可以逐份讀回，正式的報告、buffer、彙整池的已分析標記、buffer 的過期處理、兩個站的部署、
   術語收錄流程都沒有發生。
3. **Given** 一次不發布的執行已經跑完，**When** 下一次正式的排程執行開始，**Then** 它讀到的彙整池與 buffer 跟沒有那次不發布執行時相同。
4. **Given** 沒有人手動觸發，**When** 任何排程時間到了，**Then** 不會有不發布的執行自己發生。
5. **Given** 一次不發布的執行，**When** 讀它的執行紀錄，**Then** 第一行就看得出它是不發布的哪一級，而且每一種被略過的寫入與發布各有一行說明略過了什麼。

### User Story 2 - 從專案規則讀得到分片原則 (Priority: P2)

在這個專案規劃改動的人（走 spec，或直接開小 PR）打開專案規則，讀得到：改動照驗收範圍分片，一片一個 PR、各自驗收；每一片寫明驗收範圍、用什麼驗、
要不要等實跑；只有真的要看實跑的那一片等排程。規則列出驗收範圍的分類與每一類夠用的驗法。

**Why this priority**: 沒有寫成規則之前，原則只在 BACKLOG 的一個小節與不進版控的 memory 裡，下一個 spec（`GNS-20261108-2zc`）拆 task 時讀不到。

**Independent Test**: 拿 BACKLOG 小節盤點表裡的一列，只讀專案規則（不讀 BACKLOG 小節），寫出它的分片與每片的驗法；結果跟盤點表那一列的「夠用的驗法」一致。

**Acceptance Scenarios**:

1. **Given** 專案規則已更新，**When** 規劃一個同時動到收集與分析的改動，**Then** 從規則就能分出「必要的輸入」「輸出」各一片，並知道兩片都用不發布的執行驗、不等週報。
2. **Given** 一個改動裡有一部分只有實跑才看得出來（例如耗時），**When** 照規則分片，**Then** 只有那一片的驗收條件寫等排程，其他片的 merge 與完成不被它擋住。
3. **Given** 一件事是在等資料累積（例如連續幾週的數字），**When** 照規則分類，**Then** 它被歸成觀測，不寫成任何一片的驗收條件。

---

### User Story 3 - 流程接點：tasks、PR 內文、BACKLOG 列、上線後的讀回 (Priority: P3)

走 spec 時，tasks 照驗收範圍分組，每一組就是一片；直接開小 PR 時，PR 內文交代這一片的驗收範圍、驗法與結果。一個改動分成數個 PR 之後，
它在 BACKLOG 的那一列什麼時候移出、上線後才驗得到的讀回由什麼提醒，都有明確的答案。

**Why this priority**: 規則說要分片，但開 PR、移出 BACKLOG 列、翻 task 標記這些既有的流程都是照「一個 spec 一個 PR」寫的；接點沒定，分片會在每個 spec 重新談一次。

**Independent Test**: 用這個 spec 自己當第一例：它的 tasks 照驗收範圍分組、分成數個 PR，每個 PR 的內文都有那一片的驗收範圍、驗法與結果；
BACKLOG 的 `GNS-20261114-bh8` 照定下的時點移出。

**Acceptance Scenarios**:

1. **Given** 一個走 spec 的改動，**When** 產生 tasks，**Then** 每一組 task 標明它的驗收範圍與驗法，要等實跑的那一組排在不卡住其他組的位置。
2. **Given** 一個直接開的小 PR，**When** 讀它的內文，**Then** 看得到這一片的驗收範圍、用什麼驗、驗的結果，以及後面還有沒有別的片。
3. **Given** 一個功能已經上線、還有一片要等實跑讀回，**When** 讀回的日期到了，**Then** 有東西自己響，不只靠 tasks 裡沒勾的那一格與不進版控的交接檔。

---

### User Story 4 - 手上寫成「等週報」的項目改成夠用的驗法 (Priority: P4)

BACKLOG 小節的盤點表列了 10 個現在寫成等週報的項目。逐項照新原則改寫驗收條件：能用不發布的執行、重播或讀 daily 紀錄驗的就那樣驗，
只有真的要看實跑的留著等。

**Why this priority**: 這是原則第一次套用到真的項目，也是「排程不再是所有事情的時鐘」看得見的結果；它要用到第一片的跑法，所以排在後面。

**Independent Test**: 盤點表的 10 列逐列對照改寫後的驗收條件：「要等 weekly 嗎」那一欄標「不用」的 4 列與標「不用整個等」的 1 列不再寫等週報；其餘 5 列寫明為什麼只有實跑驗得到。

**Acceptance Scenarios**:

1. **Given** `#218` 的分支，**When** 用不發布的跑法在正式執行環境跑一次，**Then** 紀錄裡看得到每一條呼叫路徑讀到的是哪一組模型設定，`#218` 不必等任何一次排程週報就能判斷接線對不對。
2. **Given** 盤點表裡標「不用」或「不用整個等」的項目，**When** 讀它改寫後的驗收條件，**Then** 條件裡沒有「連兩週」「第一份週報」「週報後」這類等排程的寫法。
3. **Given** 盤點表裡仍要等實跑的項目，**When** 讀它的驗收條件，**Then** 寫明了是哪一種只有實跑驗得到的東西（耗時、換模型後的實際輸出、排程本身有沒有觸發）。

---

### Edge Cases

- 不發布的執行讀到的是觸發當下的 buffer 與彙整池，跟週一排程時不一樣：它驗的是接線與輸出對不對，不是預演週一的結果。規則與執行紀錄都要說清楚這一點。
- 不發布的執行跟正式的排程執行同時在跑：兩者互不影響，不發布的那一次不能讓排程的那一次被取消、排隊到逾時或讀到不同的資料。
- 第二級用的是正式的 LLM 額度：緊接在排程之前觸發，可能讓正式執行遇到額度不足。次數不設上限是已定的，所以每次執行要把呼叫次數印出來，讓這個代價看得見。
- 跨次執行的狀態（彙整池的已分析標記、指紋、buffer 過期、跨次去重）對不對，要看連續兩次執行；單次不發布的執行驗不到，它自己也不能寫這些狀態。
- 排程有沒有觸發，只有真的排程事件能證明；手動觸發驗不到。
- FFXIV 沒有每日的執行，輸入只有週一看得到；不發布的第一級因此是它在兩次週報之間唯一看得到輸入的方法，產物要留得住、之後能拿來重播。
- 一個改動只有一種驗收範圍：就是一片、一個 PR，不為了分片硬拆。
- 一片驗收沒過：修正是自己的一片，有自己的 PR；已經 merge 的片不因此算沒完成。
- 分類裡沒有的驗收範圍：分類是舉例，不是全部；規則要寫明遇到新的範圍時怎麼加。
- 上線後讀回的提醒只在開 session 的機器上出聲、日期也不等於那次實跑真的跑了：響了之後先確認那次執行存在，再讀。

## Requirements *(mandatory)*

### Functional Requirements

**不發布的跑法（第一片）**

- **FR-001**: 系統 MUST 在正式執行環境提供手動觸發「不發布」週報流程的入口，分兩級（已定 2026-11-14）。
- **FR-002**: 第一級 MUST 跑完收集、過濾與入選後停止，不呼叫 LLM。
- **FR-003**: 第二級 MUST 跑到分析完成並讓分析的輸出全文可以讀回，但不寫入正式資料、不發布。
- **FR-004**: 兩級都 MUST NOT 改變任何對外可見或影響之後執行的東西：正式的報告、交通的 buffer、彙整池的已分析標記、buffer 的過期處理、指紋與跨次去重的紀錄、
  兩個站的部署、術語收錄流程的連帶觸發。
- **FR-005**: 不發布的執行 MUST 只由人手動觸發，不設次數上限，MUST NOT 由排程觸發（已定 2026-11-14）。
- **FR-006**: 不發布的執行 MUST 能對還沒 merge 的版本執行。
- **FR-007**: 不發布的執行 MUST 在執行紀錄開頭標明自己是哪一級，並對每一種被略過的寫入與發布各印一行，讓「略過了」與「沒跑到那裡」分得開。
- **FR-008**: 不發布的執行 MUST 留下可以讀回的產物：每個類別的收集數、過濾後數與入選清單；第二級另有分析輸出的全文。產物之後可以拿來重播。
- **FR-009**: 第二級 MUST 在執行紀錄裡印出 LLM 的呼叫次數。
- **FR-010**: 正式排程的執行 MUST 不因這個功能而改變：同一份輸入下，寫入與發布的結果跟這個功能加入之前相同；不發布的執行 MUST NOT 取消或擋住正式的執行。

**專案規則（第二片）**

- **FR-011**: 專案規則 MUST 寫明分片原則：改動照驗收範圍分片，一片一個 PR、各自驗收；每一片寫明驗收範圍、用什麼驗、要不要等實跑；
  只有真的要看實跑的那一片等排程。走 spec 與直接開小 PR 都適用（已定 2026-11-14）。
- **FR-012**: 專案規則 MUST 列出驗收範圍的分類與每一類夠用的驗法。已定的五種（2026-11-14）：功能本身、必要的輸入、輸出、回收檢驗、修正。
  另外四類是提案（未定）：跨次執行的狀態、排程與串接、資源、觀測。分類是舉例，不是全部，規則 MUST 寫明遇到新的範圍時怎麼加。
- **FR-013**: 專案規則 MUST 寫明驗收條件的寫法：先寫最早就夠用的驗法（不發布的執行、重播、讀 daily 紀錄）；「等排程的週報」只用在其他驗法都驗不到的部分，並寫明為什麼驗不到。
- **FR-014**: 專案規則 MUST 寫明它蓋過 user 層「一個 spec 一個 PR」的範圍只限這個專案（已定 2026-11-14）。
- **FR-015**: 專案規則 MUST 放在 [NEEDS CLARIFICATION: 寫在憲章（進版控、雲端 session 讀得到，修訂要升版並經過一輪 cold review），還是本機的在地設定（只有這台機器讀得到）？]

**流程接點（第三片）**

- **FR-016**: 走 spec 時，tasks MUST 照驗收範圍分組，每一組是一片：標明驗收範圍與驗法，對應一個 PR；要等實跑的那一組 MUST 排在不卡住其他組的位置。
- **FR-017**: 直接開的小 PR，內文 MUST 交代這一片的驗收範圍、驗法與結果；後面還有別的片時寫明剩哪些。
- **FR-018**: 一個改動分成數個 PR 時，它在 BACKLOG 的那一列 MUST 在 [NEEDS CLARIFICATION: 哪一片的 PR 移出——第一片、最後一個 merge 前驗得完的片，還是連上線後的讀回都過了才移出？]
- **FR-019**: 功能上線之後才驗得到的部分 MUST [NEEDS CLARIFICATION: 算不算這個 spec 的一環——算（spec 開到讀回過了才關）、不算（spec 只收 merge 前驗得到的，其餘當觀測），
  還是分成「上線」與「驗收完成」兩個時點（讀回是同一個 spec 的一片，有自己的 PR 與自己的一列 BACKLOG）？2026-11-14 的傾向是第三種，未定案。]
- **FR-020**: 上線後的讀回 MUST 有一個會自己響的提醒，不只靠 tasks 裡沒勾的那一格與不進版控的交接檔；提醒響了之後 MUST 先確認那次執行存在再讀。
  （怎麼響取決於 FR-019 的答案；用到的日期宣告在 user 層，記在 bare 的 `GUB-20261114-gw7`。）

**套用到手上的項目（第四片）**

- **FR-021**: BACKLOG 小節盤點表的每一個項目 MUST 照新原則改寫驗收條件，寫明夠用的驗法與要不要等實跑。
- **FR-022**: `#218` 的接線 MUST 用不發布的跑法在正式執行環境驗一次，結果記在那個 PR 上，之後才 merge（已定 2026-11-14）。

### Key Entities

- **片**：一個改動裡驗收範圍相同的部分；有自己的驗法、自己的 PR、自己的驗收結果。
- **驗收範圍**：一片要證明的是哪一種東西（功能本身、必要的輸入、輸出、回收檢驗、修正……），決定用什麼驗、要不要等實跑。
- **不發布的執行**：在正式執行環境手動觸發、不留下對外可見或影響之後執行的痕跡的一次週報流程；分兩級。
- **觀測**：在等資料累積的事（連續幾週的數字）；不是任何一片的驗收條件。
- **讀回**：功能上線之後，讀某一次實跑的結果來完成的驗收；屬於「回收檢驗」。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 不發布的兩級各在正式執行環境成功跑過至少一次；每一次觸發前後，正式資料的五個計數（報告數、buffer 筆數、彙整池未分析筆數、兩個站的最後部署時間、
  術語收錄流程的執行次數）完全相同。這是第一片的 Gate。
- **SC-002**: 第一級的執行紀錄裡 LLM 呼叫是 0 次；第二級的分析輸出每一份都能從產物讀回全文。
- **SC-003**: `#218` 的接線在第一片 merge 之後、不經過任何一次排程週報，就取得一次不發布的實跑紀錄，紀錄裡有每一條呼叫路徑讀到的模型設定。
- **SC-004**: 盤點表的 10 個項目裡，「要等 weekly 嗎」那一欄標「不用」的 4 個與標「不用整個等」的 1 個，改寫後的驗收條件不再出現等排程的寫法；其餘 5 個各寫明只有實跑驗得到的是什麼。
- **SC-005**: 這個 spec 自己分成至少 2 個 PR 出貨，每個 PR 的內文都寫明那一片的驗收範圍、驗法與結果。
- **SC-006**: 加入這個功能之後的第一次正式排程週報，寫入與發布的項目跟前一週同類（報告、buffer、彙整池標記、兩個站的部署、術語收錄的連帶觸發都照常發生），沒有任何一項被不發布的邏輯略過。
  這一條只有實跑驗得到，是這個 spec 自己的回收檢驗。

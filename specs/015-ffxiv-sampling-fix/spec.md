# Feature Specification: FFXIV 週報取樣修正

**Feature Branch**: `015-ffxiv-sampling-fix`  
**Created**: 2026-10-20  
**Status**: Draft  
**Input**: BACKLOG `GNS-20261019-a0r`（FFXIV 週報只剩 Reddit：論壇來源改追最後回覆、篩選加來源權重）。
Luke 10-19 定範圍、10-20 裁示：`GNS-20261019-3cq` 不併入；`GNS-016` 只接「回 200 但 0 筆要出聲」那一半。

## 背景：為什麼週報只剩 Reddit

09-21～10-19 五次週報，FFXIV 分析的 20 篇全是 Reddit 的英文貼文，標題含漢字或假名的 0 篇。成因不在來源，在取樣：

- 篩選的最後一步依發布時間由新到舊取前 20 篇，沒有來源權重。Reddit `new` 的 25 篇是最近約半天（10-19 量 15.7 小時），
  永遠排最前；HTML 來源沒有發布時間，永遠排最後。
- 論壇各版的 RSS 依開串時間排序，舊串有新回覆不會出現；內容只取約 100 字的摘要，全文其實在 RSS 裡。
- Lodestone 五週都是 `0 筆`：設定的 selector 對不到任何項目，而且指到的分類是「メンテナンス」，不是「アップデート」。
  這個 `0 筆` 記成 INFO、不算失敗，所以五週都沒人發現。

10-20 實測（本機與 Actions 同一分鐘逐行相同，PR `#173`）：依最後回覆排序的 RSS 五個版都打得到、每篇帶全文；
討論串頁面不必登入讀得到；Lodestone 的アップデート分類對到 20 則。

**供給量**（10-20 本機量，單週，實測）：7 天內有回覆的串 537＝0、550＝0、551＝2、552＝1、553＝3，合計 6 串；
Lodestone アップデート 7 天內 1 則、28 天內 7 則。名額是 20，所以問題不是不夠，是被擠掉。

## Clarifications

- Q: 上線後怎麼決定輸出形式要不要改？ → A: 觀察約一週；候選池的供應遠大於 20 篇時，開始考慮調整 FFXIV 的輸出形式——
  對齊交通週報（彙整），或第三套方法。供應讀自 FR-010 的候選池逐來源篇數。
- Q: `GNS-016`（PTT 每天失敗）要不要一起做？ → A: 只做共用的「回 200 但解析出 0 項要出聲」；PTT 在 Actions 上 403 的成因留在 `GNS-016`。
- Q: 入選的 20 個名額怎麼分？ → A: 純權重排序——權重高的來源先入選，同權重依時間新到舊，沒有時間的排最後。
  順序：PLL ＞ 四個 class & jobs 版 ＞ Lodestone ＞ TW 修正說明 ＞ Reddit ＞ 論壇列表頁（只有標題）。
  以 10-20 的供給，論壇＋官方約 6～8 篇，Reddit 仍拿約 12 篇；大 patch 後論壇爆量時 Reddit 可能很少，接受。
- Q: 每串在兩次收集之間的其他回覆怎麼處理？ → A: 去討論串頁面拿窗口內的回覆（從最後一則那頁往前翻，有上限），合成一篇；
  只拿最後一則撐不起「這週在討論什麼」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 週報的 FFXIV 分析看得到日文論壇的玩家討論 (Priority: P1)

使用者（Luke）讀 FFXIV 週報，想知道日本玩家這週在職業平衡、戰鬥系統上討論什麼。現在 20 篇全是 Reddit 英文貼文，
官方論壇的 class & jobs 四個版與 PLL 版一篇都進不來。使用者要：這週有新回覆的論壇串會進分析，分析看得到這週窗口內的回覆全文。

**Why this priority**: 這是 `a0r` 的完成標準，也是這個 spec 的目的。

**Independent Test**: 讀週報 log 的逐來源入選篇數（FR-010），數五個論壇版的篇數；對照同一週 RSS 裡窗口內的串數。

**Acceptance Scenarios**:

1. **Given** 某版這週有 3 串有新回覆，**When** 週報執行，**Then** 那 3 串都進入分析，每串的內容是這週窗口內的回覆全文
   （上限內），不是截斷的摘要。
2. **Given** 一個長期串這週有 30 則新回覆、上限是 N 則，**When** 收集，**Then** 收最新的 N 則，log 記下「窗口內 30 則、收 N 則」。
3. **Given** 一個長期串上週已分析過、這週又有新回覆，**When** 週報執行，**Then** 它以這週的回覆再次進入分析，不含上週已分析的回覆。
4. **Given** 一串上週已分析過、這週沒有新回覆，**When** 週報執行，**Then** 它不再進入分析。
5. **Given** 某版回傳的串數達上限、而且最舊那串仍在收集窗口內，**When** 收集，**Then** log 印出截斷警告（版名、最舊那串的時間）。
6. **Given** 討論串頁面這次抓不到，**When** 收集，**Then** 那串退回只用 RSS 的最後一則，log 印出退回的原因。

---

### User Story 2 - PLL 有新串時一定進分析 (Priority: P1)

プロデューサーレターLIVE 不定期、間隔長，但每一次都是當期最重要的官方資訊。使用者要：只要 PLL 版有窗口內的串，
它就一定在入選的 20 篇裡，不管其他來源這週多熱鬧。

**Why this priority**: Luke 10-19 明定 PLL 權重最高。PLL 不定期，上線後兩週內可能剛好沒有 PLL，所以這條要靠測試證明，不能等。

**Independent Test**: unit test：PLL 一篇與 25 篇發布時間更新的 Reddit 並存時，PLL 入選；把 PLL 的權重調低，測試轉紅。

**Acceptance Scenarios**:

1. **Given** PLL 版有 1 串窗口內的新回覆、Reddit 有 25 篇更新的貼文，**When** 篩選，**Then** PLL 那串入選。
2. **Given** 各來源的權重寫在設定裡，**When** 讀設定，**Then** 看得出 PLL 最高、其他來源的相對順序。

---

### User Story 3 - Lodestone 的アップデート進得來 (Priority: P2)

Lodestone 五週都是 `0 筆`。使用者要：アップデート公告進得了收集，而且只收窗口內的，不會在修好的那一週把幾個月的舊公告一次灌進來。

**Why this priority**: 官方公告量少（28 天 7 則），但它也是 `3cq` 之後 patch 偵測的前提。

**Independent Test**: 讀週報 log 的 Lodestone 那一行：解析到幾則、窗口內幾則。

**Acceptance Scenarios**:

1. **Given** アップデート分類頁有 20 則公告、其中 1 則在窗口內，**When** 收集，**Then** 解析到 20 則、收進 1 則，兩個數字都印在 log。
2. **Given** 修好後的第一次週報，**When** 收集，**Then** 窗口外的舊公告不進入分析。

---

### User Story 4 - 爬蟲解析出 0 項時會出聲 (Priority: P2)

Lodestone 的 selector 失效五週沒人發現，因為「回 200 但 0 筆」只記成 INFO。PTT 也有同一個形狀（`GNS-016`）。
使用者要：HTML 爬蟲與 PTT 的頁面回應成功、卻一個項目都解析不到時，記成失敗，出現在 `來源失敗` 那一行。

**Why this priority**: 它不提高本週的取樣品質，但能讓下一次 selector 失效在當週就被看到。

**Independent Test**: unit test：餵一個 selector 對不到的頁面，失敗名單含該來源；餵一個有項目但全被篩掉的 PTT 頁面，失敗名單不含。

**Acceptance Scenarios**:

1. **Given** Lodestone 的頁面改版、selector 對到 0 個項目，**When** 收集，**Then** `來源失敗` 名單含 Lodestone。
2. **Given** PTT 看板有文章、但推文數都不到門檻，**When** 收集，**Then** 不算失敗（0 篇是篩選結果，不是解析失敗）。
3. **Given** 論壇某版 RSS 回傳 0 串，**When** 收集，**Then** 不算失敗（PLL 不定期，0 是常態）。

---

### Edge Cases

- **某版窗口內 0 串**（10-20 的 537、550）：不出聲、不算失敗，名額給其他來源。
- **截斷**：一個版一次最多回 15 串。第 15 串仍在窗口內時，可能有串被截掉，印警告；10-20 的 553 第 15 串停在 09-24，不會觸發。
- **長期串**（例：「獣使いスレ」）：標題每週相同，內容每週不同。跨週去重若只比標題，第二週起會被擋；本 spec 要它能再進來（FR-003）。
- **PLL 開子版**：過去 PLL 會開「第N回」子版，父版 RSS 含不含子版的串沒驗。近期的子版 id 遠小於現在的串 id（推論：已不再開子版），
  但上線前要查證（FR-011）。
- **Lodestone 第一次修好**：窗口外的舊公告（28 天內就有 7 則）不得一次湧入。
- **沒有發布時間的來源**（TW 修正說明、論壇列表頁）：排序規則要明確處理，不能因為權重而每週固定佔名額。
- **Reddit 被擠出**：論壇與官方的供給一週約 6～8 篇，Reddit 仍拿得到剩下的名額；不是把 Reddit 換成另一種單一來源。
- **全文很長**（一週幾十則回覆、引用、圖片）：每串收的回覆數有上限，分析的輸入長度上限照現行做法，不因全文而失控。
- **窗口內的回覆跨好幾頁**：往前翻的頁數有上限；到上限還沒翻到窗口起點時，log 記下「可能還有更早的回覆沒收」。
- **討論串頁面抓不到或解析不出回覆時間**：那串退回只用 RSS 的最後一則，印出原因；不得整串丟掉，也不得沉默退回。
- **0 項計入失敗比例**：traffic daily 的來源失敗超過一半會中止；PTT 的解析 0 項計入，與現在的 403 一樣處理。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 五個論壇版（537 プロデューサーレターLIVE、550 TANK、551 DPS、552 HEALER、553 その他バトルシステム）MUST 改用
  依最後回覆排序的 RSS；每串的內容取 RSS 裡那則回覆的全文，不再只用截斷摘要。
- **FR-002**: 一個版回傳的串數達上限、且最舊那串的最後回覆仍在收集窗口內時，MUST 印截斷警告（版名、最舊那串的時間）。
- **FR-003**: 同一串在之後的週有新回覆時，MUST 能再次進入分析；新舊以回覆為單位判斷，不以串標題。
  同一則回覆不得被分析兩次。
- **FR-004**: 篩選留下的篇數 MUST 依來源權重純排序：權重高的來源先入選，同權重依時間新到舊，沒有時間的排最後。
  權重寫在設定裡，未寫的來源用預設權重。順序：PLL ＞ 四個 class & jobs 版 ＞ Lodestone ＞ TW 修正說明 ＞ Reddit ＞ 論壇列表頁。
- **FR-005**: FR-004 的排序 MUST 有 unit test 鎖住：PLL 與更新的 Reddit 並存時 PLL 入選；把 PLL 權重調低時測試轉紅。
  測試用字面值寫權重，不引用設定常數。
- **FR-006**: Lodestone MUST 改抓「アップデート」分類，selector 對到實際的公告項目；每則帶發布時間，只收窗口內的。
  log MUST 同時印「解析到幾則」與「收進幾則」。
- **FR-007**: HTML 爬蟲（`html_patch`、`html_forum`）與 PTT：頁面回應成功、但解析出 0 個項目時，MUST 記成來源失敗，
  出現在 `來源失敗` 名單。解析出項目、但全被篩掉（例：PTT 推文數門檻）不算；RSS 回傳 0 篇不算。三種爬蟲共用同一個判斷，有 unit test。
- **FR-008**: 每串 MUST 收窗口內的回覆：從最後一則所在那頁往前翻，到窗口起點、回覆數上限或頁數上限為止，合成一篇。
  兩個上限寫在設定裡。每串 log 記下「窗口內幾則、收幾則、翻了幾頁」；抓不到頁面或解析不出回覆時間時，退回只用 RSS 的最後一則，
  並印出原因（每一種放棄原因各自一句，分得開）。
- **FR-009**: FFXIV 週報的節奏（每週一份）與分析篇數上限（20）MUST NOT 改變；patch-triggered 與聚合 digest（`3cq`）不在範圍。
- **FR-010**: 週報 log MUST 印出 FFXIV 候選池（篩選後、截到 20 篇之前）與入選 20 篇的逐來源篇數，使 SC-001 與
  輸出形式的判斷（Clarifications）不必查資料庫或逐篇讀標題就能判讀。
- **FR-011**: 上線前 MUST 查證 PLL 父版（537）的 RSS 是否包含子版的串，結果寫進 research；不包含時另接子版，或寫明缺口。
- **FR-012**: 每項變更 MUST 可單獨回復（例：論壇 RSS 回到不帶最後回覆排序的網址、權重全部設成相同），回復後行為回到變更前。

### Key Entities

- **來源**：FFXIV 來源清單中的一筆（名稱、型別、URL、啟用與否、權重）。五個論壇版各算一個來源。
- **論壇項目**：一串在某次收集窗口內的回覆合成的一篇（串標題、各則回覆的全文與時間、連結）。同一串不同週是不同項目，
  回覆不重疊。
- **來源權重**：決定篩選優先序的數字。PLL 最高；未寫的來源用預設值。
- **收集窗口**：只收最後回覆（或發布時間）在窗口內的項目；沿用現行的 7 天。
- **入選篇數**：某來源在某週進入 FFXIV 分析（最多 20 篇）的篇數。

## Success Criteria *(mandatory)*

**量測前提**：入選篇數讀自 FR-010 的 log；窗口內可用串數由同一週 RSS 重算（週驗收 routine 或本機）。硬門檻只收實測。

### SC-001 論壇內容進分析（本 spec 的主要目標）

- **SC-001 L0 / Gate**：上線後連兩週，分析的 20 篇裡至少 1 篇來自五個論壇版（`a0r` 的完成標準）。
  錨定：09-21～10-19 五週都是 0／20；10-20 窗口內可用 6 串，只要不被擠掉就過得了。
- **SC-001 L1**：連兩週，窗口內每一串（去重後）都進分析，論壇版入選數等於可用串數。錨定：可用 6 串，遠小於 20 個名額。
- **SC-001 L2 / 理想**：連兩週，論壇項目的分析至少一半人工判讀為「講得出這週在討論什麼」（逐篇判讀，結果寫進驗收紀錄）。
  錨定：無——這是第一次讓論壇內容進分析，先量第一次的數字。

### SC-002 Lodestone

- **SC-002 Gate**：每週 Lodestone 解析到的項目 > 0。錨定：五週都是 0；10-20 解析 20 則。
- **SC-002 L1**：窗口內有アップデート公告的那一週，它進分析。錨定：28 天內 7 則，平均每週 1～2 則。

### SC-003 PLL 優先（硬門檻，測試）

- FR-005 的 unit test 存在且咬得到：照實作跑是綠的；把 PLL 權重調低（突變），對的那條轉紅。

### SC-004 0 項會出聲（硬門檻，測試＋實測）

- FR-007 的 unit test 存在且咬得到。
- 實測：在修 Lodestone 之前，用現行（錯的）selector 跑一次收集，`來源失敗` 名單含 Lodestone——證明五週的沉默在新規則下會被看到。

### SC-005 runtime 與成本

- **硬門檻**：上線後週報每次都在 `timeout-minutes`（30 分）內完成。錨定：10-19 週報 10m15s，FFXIV 那段 3.8 時期 292–352 秒。
- 記錄：論壇全文與窗口內回覆讓分析輸入變長、收集多了討論串頁面的請求，報出 FFXIV 那段的耗時、請求數與 token 變化（不設門檻）。

### SC-006 候選供應（記錄）

- 上線後第一次週報起，記下候選池的總篇數與逐來源篇數（FR-010），不設門檻。這是 `3cq` 新觸發點要讀的數字：
  約一週後遠大於 20 篇，就開始考慮調整輸出形式。錨定：10-19 原始收集約 54 筆（Reddit 25、論壇列表 15、TW 修正說明 5、論壇 RSS 9、Lodestone 0）。

### 驗收時點

- **closeout**：上線、SC-003／SC-004 通過、第一次週報跑完且 SC-002 Gate 過，就收 PR。
- **closeout 之後**：SC-001 的兩週判定交給週驗收 routine（`FOCUS.md` 加一項）。closeout 時 `a0r` 那一列移出，換成一列追 SC-001；
  `3cq` 的觸發點改成「本 spec 上線約一週後，候選池遠大於 20 篇時，考慮調整輸出形式（對齊交通週報的彙整，或第三套方法）」；
  `GNS-016` 那一節記下觸發點被踩到、只接了「0 項出聲」那一半。

## Assumptions

- **收集窗口沿用 7 天**，FFXIV 每週收集一次；「上次抓取」就是窗口起點。
- **分析流程不動**：每篇各自分析、上限 20 篇、輸入長度上限照現行。
- **論壇列表頁（只有標題）與 TW 修正說明照舊啟用**；它們在新排序裡的位置由 FR-004 的答案決定。
- **Actions 打得到所有新網址**（PR `#173`，10-20 實測）。
- **討論串頁面上每則回覆的時間解析得出來**：10-20 只驗了頁面讀得到、內文在上面，時間的格式與往前翻頁的網址沒驗，plan 的 research 先驗。
- **不動 traffic 的取樣**；PTT 只動「解析 0 項」的判斷，不動推文數門檻與 403。

## 已知限制（誠實標註）

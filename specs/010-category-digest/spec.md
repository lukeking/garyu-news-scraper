# Feature Specification: 低頻類別聚合式深度分析（category digest，交通週報）

**Feature Branch**: `010-category-digest`
**Created**: 2026-07-13
**Status**: Draft
**Input**: User description: "低頻類別聚合式深度分析（category-level digest，交通週報）——道安政策 類在收集/去重/路由全修復後仍結構性無法產出熱點報告（全部單篇 bucket，分數天花板 ≈ 0.22 vs 門檻 1.0）。量觸發＋消耗：類別池累積達門檻即產出一份多事件彙整報告，發布後池歸零；沿用既有 hot_topic_report 管線，零 schema／零前端變更。"

## 背景（為什麼需要這個 feature）

2026-07-13 驗證（run 29217421005 ＋ 本地 read-only 重放，重放分數與 run log 完全吻合）確認：道安政策 類的供給側問題已全數修復（收集 PR #58、跨週去重＋豁免 PR #60、路由驗證正確、門檻下修 PR #59），但該類**仍然發不出報告**，且原因是結構性的——

政策報導只有兩種型態：同一事件多家轉載＝標題近同 → 近重複去重「留一刪一」，組不成多篇 bucket；不同事件（各縣市道安會報、工作坊、政策發布）＝標題互異 → 各自成單篇 bucket。能聚類的「相關但不同」帶對政策文幾乎不存在。單篇 bucket 的分數上限 ≈ 0.48 × quality ≈ 0.22，門檻 1.0 永遠打不到。buffer 實況：15 篇道安政策文（跨 4 週）全是 singleton，0.079–0.222 分。

這不是 tuning 問題，是評分公式對「事件發散型類別」的結構問題。解法＝為指定的低頻類別開一條**聚合路徑**：不等單一事件長成大 bucket，而是等類別池累積夠多獨立事件後，產出一份彙整型深度分析。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 低頻類別的彙整報告終於出現 (Priority: P1)

身為週報讀者，我希望道安政策這類低頻但高價值的內容，在累積了足夠素材後能以「一段期間政策動態總覽」的形式出現在週報，而不是因為每則新聞都是獨立事件而永遠缺席。

**Why this priority**: 這是本 feature 的存在理由。道安政策 自管線上線以來發布數為 0，供給側已修好、素材已在池內，只差觸發機制。

**Independent Test**: 在池內文章數達觸發門檻的狀態下跑週分析 → 產出一份該類彙整報告並照常發布（與既有熱點同版位可見）；在未達門檻的狀態下跑 → 不產出、池繼續累積。

**Acceptance Scenarios**:

1. **Given** 道安政策 池內有效文章數 ≥ 觸發門檻，**When** 週分析執行，**Then** 產出一份 topic_label 為「道安政策 · 彙整」樣式的深度分析報告，內容涵蓋池內多個獨立事件，經既有發布管線上頁。
2. **Given** 池內有效文章數 < 觸發門檻，**When** 週分析執行，**Then** 不產出 digest、不消耗任何文章，池繼續累積。
3. **Given** digest 已成功發布，**When** 檢視報告，**Then** 其來源文章清單、來源數、天數等欄位反映實際選材的池內容。

---

### User Story 2 - 彙整過的內容不重複出現 (Priority: P2)

身為週報讀者，我不希望在下一份彙整報告裡再看到上一份已經講過的政策新聞。

**Why this priority**: 消耗語意是「量觸發」設計的另一半——沒有它，同一批文章每週重複觸發、重複發布。它同時讓節奏自然形成：新聞多就密、新聞少就疏。

**Independent Test**: 連續模擬兩次觸發：第一次 digest 發布後，驗證池內文章全部標記為已分析；第二次 digest（若再觸發）的來源文章與第一次零交集。

**Acceptance Scenarios**:

1. **Given** digest 成功持久化，**When** 檢查 buffer，**Then** 該類別池內全部文章（含未入選材的低品質文）都已標記為已分析，池歸零。
2. **Given** digest 的深度分析或持久化失敗，**When** 該次週分析結束，**Then** 池內文章**不被消耗**，下次週跑重試觸發。
3. **Given** 兩份先後發布的 digest，**When** 比對來源文章清單，**Then** 零重複。

---

### User Story 3 - 垃圾素材不進彙整 (Priority: P3)

身為週報讀者，我不希望彙整報告把「友善列印」這類爬蟲撿到的垃圾標題當成政策動態來介紹。

**Why this priority**: 已知風險（relevance 豁免的代價，buffer 內已有實例：「友善列印 - 新竹市政府交通處」，quality 0.165）。單篇 bucket 路徑靠門檻自然擋掉它，聚合路徑必須有自己的防護。

**Independent Test**: 在池內混入 quality 低於下限的文章後觸發 digest → 驗證該文不出現在報告來源清單，也不計入觸發門檻的計數，但發布後同樣被消耗（清池）。

**Acceptance Scenarios**:

1. **Given** 池內含 quality < 品質下限的文章，**When** 統計觸發門檻，**Then** 該文不計入有效篇數。
2. **Given** digest 觸發並發布，**When** 檢視選材，**Then** 選材全部 quality ≥ 品質下限，且該垃圾文仍隨清池被標記為已分析（不會永久滯留）。

---

### Edge Cases

- **同週同類別出現過門檻的一般 bucket**（罕見但可能，如重大政策發布多家跟進成 cluster）：一般 bucket 的單事件深挖優先發布；該 bucket 的文章不重複進 digest 選材。digest 觸發計數以池內其餘文章計。
- **池永遠達不到門檻**：文章依既有 8 週 buffer 到期機制過期消失。v1 接受此損耗（不做到期前強制 flush）——依實測流入量（約 3–4 篇/週）門檻會在 3 週左右觸發，餓死風險低；若實際觀察到成批過期再議。
- **觸發成立但當週一般熱點已滿 3 格**：digest 優先佔一格（見 FR-007）——本 feature 的目的就是反餓死，若又被高頻類別排擠則功能失效。
- **分析或持久化失敗**：不消耗、下次重試（US2 場景 2）。失敗當週其他一般熱點照常發布。
- **多個類別同時啟用 digest 且同週同時觸發**：各自獨立產出，各佔一格；若超過上限，依有效篇數多者優先，其餘留待下週（池未消耗，不損失）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 啟用聚合的類別集合、各類別觸發門檻（有效篇數）與品質下限 MUST 由管線設定檔控制（比照既有 per-category 門檻的設定模式）；未列入設定的類別，行為與現狀完全一致。
- **FR-002**: 每次週分析 MUST 對每個啟用類別統計池內「有效文章數」（quality ≥ 品質下限者），達門檻即觸發 digest 產出；未達則不動作。
- **FR-003**: digest MUST 沿用既有深度分析報告實體與發布管線：topic_label 採「<類別> · 彙整」樣式，累積分數、來源數、天數、來源連結等欄位按實際選材計算；前端與資料 schema 零變更。
- **FR-004**: digest 內容 MUST 為多事件彙整型（該期間政策動態總覽，逐事件帶出脈絡），選材為池內 quality 由高至低至多 K 篇（K 可設定，預設 15）。
- **FR-005**: digest 成功持久化後 MUST 將該類別池內**全部**文章（含未入選材者）標記為已分析（消耗、池歸零）；任一環節失敗則 MUST NOT 消耗任何文章。
- **FR-006**: 同週該類別若有一般 bucket 通過門檻並發布，該 bucket 之文章 MUST NOT 重複進入 digest 選材。
- **FR-007**: 觸發成立的 digest MUST 在既有報告數上限（3）內優先佔位；剩餘名額才由一般 bucket 依既有規則競爭。digest 不參與一般 bucket 的分數排序，也不經 novelty gate（消耗語意已保證跨期無重複）。
- **FR-008**: 品質下限 MUST 可由設定調整，且預設值 MUST 能排除已知垃圾案例（quality 0.165 的「友善列印」）而保留已驗證的實質文章（quality ≥ 0.19）。
- **FR-009**: 每次週分析 MUST 在 log 記錄每個啟用類別的池狀態（有效篇數／門檻／是否觸發／消耗筆數）——**無論是否觸發**。（教訓：低於門檻靜默跳過無 log，導致 07-06、07-13 兩次驗證都得靠重放才能還原真相；本 feature 的可觀測性是驗收項目。）

### Key Entities

- **類別聚合池（category pool）**: 某啟用類別在 buffer 內全部未分析、未過期的文章。非新實體——是既有 buffer 的一個查詢視角；「消耗」即沿用既有的已分析標記。
- **彙整報告（digest）**: 既有深度分析報告實體的一種用法（以 topic_label 樣式區別），非新報告型別。
- **聚合設定（digest config）**: per-category 的觸發門檻、品質下限、選材上限 K；存於既有管線設定檔。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 道安政策 池累積達門檻後的第一次週跑即發布該類第一份彙整報告（歷史發布數 0 → 1）。
- **SC-002**: 任兩份先後發布的同類 digest，來源文章零重複（消耗語意可由資料直接驗證）。
- **SC-003**: 任何 digest 的來源清單中，quality 低於下限的文章出現數為 0（已知垃圾案例可驗證）。
- **SC-004**: 未啟用聚合的類別，發布行為與現狀零差異（回歸：既有測試全綠、一般熱點選取結果不變）。
- **SC-005**: 僅憑週跑 log 即可回答「池內幾篇／差多少觸發／消耗了幾篇」——驗證不再需要本地重放。

## Assumptions

- **觸發度量用「有效篇數」而非累積分數總和**：篇數透明、可從 log 直接驗證；分數的結構性天花板正是本 feature 要繞過的東西，不宜再拿來當觸發依據。
- **預設觸發門檻 10 篇**：依實測流入量（15 篇／4 週）約每 2–3 週觸發一次，接近「政策月報」的自然節奏；數值可調，plan 階段不需重新論證。
- **預設品質下限 0.18**：位於已知垃圾（0.165）與已驗證實文最低值（0.193）之間；可調。
- **digest 佔用既有 3 格上限的一格**（不擴格）；gate-then-cap 順序不變。
- **v1 接受「池不觸發則文章隨 8 週到期消失」**的損耗，不做到期前強制 flush。
- **接受「有效但超出選材上限 K 的文章」隨清池消耗、不出現在任何 digest**：選材為 quality 降冪，被放棄的是池內最低分的合格文章。預設節奏（門檻 10、K=15）下需單次觸發前累積超過 15 篇才會發生；出現即為觸發節奏過慢的訊號，以調整 `trigger_count`／`max_articles` 因應。
- **FFXIV 管線不在本 feature 範圍**：已決策先在 traffic 驗證聚合可行；FFXIV 另有日文來源不足的前置問題（見 memory `project_ffxiv_pipeline_direction`）。
- 沿用既有每週一分析節奏；觸發檢查掛在既有週跑流程內，不做 event-driven。

## Out of Scope

- FFXIV pipeline 套用聚合（deferred，觸發條件＝traffic 驗證可行）。
- 新報告型別欄位／前端獨立版位（已否決：沿用現有管線與版位）。
- event-driven／每日觸發。
- 一般 bucket 評分公式與流程的任何變更（聚合是選取層的平行路徑）。
- 到期前強制 flush（v1 接受損耗，見 Assumptions）。

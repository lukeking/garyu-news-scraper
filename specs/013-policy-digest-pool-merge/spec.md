# Feature Specification: 政策 digest 池匯流兄弟政策類別

**Feature Branch**: `013-policy-digest-pool-merge`  
**Created**: 2026-08-10  
**Status**: Draft  
**Input**: BACKLOG #8「政策池的單一 feed 依賴」——08-03／08-10 兩個觀察點都判定承重，轉行動。

## 背景：為什麼不是「補來源」

BACKLOG #8 原本的行動計畫是**補政策來源**。2026-08-10 查證後**該前提不成立**，本 spec 因此
換了解法。這段記錄推翻的過程，避免下次有人再從「補來源」重新出發。

07-20 加的六個政策來源自那時起**產出 179 篇**——它們沒有不產出。但只有
`Google News 交通安全教育` 進得了政策池（88/91＝97%），而原因**不是它產量大**：

- 它在 `source_defaults` 對映到 `道安政策`，且它的標題**不帶任何分類 token**，
  於是 `assign_category` 判為 `uncategorised` → fallback 生效 → 整批進政策池。
- 其餘來源的標題**帶了 taxonomy token**（`禁行`→路權政策、`行人`→行人事故、`路口`→路口安全），
  分類直接命中，**`source_defaults` 這條 fallback 永遠不會觸發**（它只在 `uncategorised` 時生效）。

而 `道安政策` 的分類關鍵字只有 **`[道安, 道安會, 願景]`** 三個。配置註解自己寫著
「禁行/兩段/行人 已是 taxonomy 關鍵字且排在事故類之前，**會自行正確落位**」——
**這是刻意設計，不是 bug**。問題出在下游：`category_digest` 只設了 `道安政策` 一個，
而 `路權政策`／`科技執法`／`交通工程` 遠低於熱點門檻 `min_threshold: 1.5`，
**永遠不會發布**。它們的內容被收集、被儲存、然後丟掉。

**所以政策池不是缺來源，是政策內容被分類法切碎在門檻之下。** 這與 spec 010 是同一個結構
（010 用 digest 解了 `道安政策` 那一層），也與 BACKLOG #9 同源。

**兄弟類別的來源比政策池本身分散一倍**（07-20 起，E1）：

| | 篇 | distinct_sources | 最大來源佔比 |
|---|---|---|---|
| `道安政策`（現行池） | 120 | **4** | **73%** |
| `路權政策`＋`科技執法`＋`交通工程` | 33 | **8** | **24%** |

## Clarifications

### Session 2026-08-10

- Q: 匯流後池變大但 `max_articles` 不變，多出的內容被消耗卻不發布——要不要調上限？ → A: 維持 25（Option B）
- Q: 匯流後報告標題仍是「道安政策 · 彙整」但內容含科技執法／路權／工程——標籤要不要改寬？ → A: 維持原標籤（Option A）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 政策彙整不再靠單一 feed 撐 (Priority: P1)

讀者每週收到的「道安政策 · 彙整」目前有 68–76% 的內容來自同一個 Google News query。
若那個 query 改變行為或被限流，報告會直接消失，而**唯一的徵兆是報告不再出現**——
不會有錯誤訊息。使用者要的是這份報告的存在**不再繫於單一外部查詢**。

**Why this priority**: 這是本 spec 唯一的目的。兩個觀察點（08-03／08-10）都判定承重，
且集中度不降反升（消耗池佔比 73%→75.7%），等待已被證明無效。

**Independent Test**: 對任一週的 buffer 快照，計算「抽掉最大來源後的有效篇數」，
比對 `trigger_count`。這個判定完全在既有資料上可算，不需要等新資料。

**Acceptance Scenarios**:

1. **Given** 某週 buffer 中政策池有效篇數 35、最大來源佔 28 篇，**When** 匯流兄弟政策類別，
   **Then** 有效篇數上升且抽掉最大來源後仍 ≥ `trigger_count`（承重解除）。
2. **Given** 匯流設定為空清單，**When** 執行週分析，**Then** 行為與匯流前**逐篇相同**
   （本功能預設不改變任何既有行為）。

---

### User Story 2 - 被丟掉的政策內容進得了報告 (Priority: P2)

`路權政策`／`科技執法`／`交通工程` 三類的內容（路權鬆綁、科技執法設點、待轉區工程）
是真實的道安政策題材，目前收進來後永遠不會出現在任何報告裡。使用者要這些內容
能被消耗，而不是只佔資料庫。

**Why this priority**: 這是 P1 的副產品而非獨立目標——匯流一旦成立，這件事自動發生。
單獨拿掉 P1 只做 P2 沒有意義。

**Independent Test**: 匯流後檢查 `hot_topic_analyzed` 標記，確認兄弟類別文章確實被消耗。

**Acceptance Scenarios**:

1. **Given** 兄弟類別中有本週文章，**When** digest 觸發並發布，**Then** 這些文章被標記為已消耗，
   不會在下週重複進池。

---

### User Story 3 - 匯流名單可調且可逆 (Priority: P3)

匯流哪些類別是編輯決定，會隨報告定位調整。使用者要能改設定就改變匯流範圍，
不必動分類法、不必重跑歷史資料。

**Why this priority**: 降低決策成本與回滾成本，但不影響 P1 是否達成。

**Independent Test**: 改設定清單、重跑，觀察池組成隨之改變；清空清單即回到匯流前行為。

**Acceptance Scenarios**:

1. **Given** 匯流清單含三個類別，**When** 移除其中一個，**Then** 該類別文章不再進池，
   且**文章本身的分類標記不變**（buffer list 的細分類保留）。

---

### Edge Cases

- **匯流清單含不存在的類別名**：**在設定載入時記一筆 WARNING（列出該名稱），然後略過該項**，
  不得使 digest 失敗。
  ⚠️ 本條原寫「忽略該項」，2026-08-10 plan 階段修正——憲章原則 I 明文
  **「silent failures are forbidden」**，靜默忽略會直接違憲。fail-soft 的價值
  （不因一個打錯的類別名讓整份週報掛掉）與憲章要求（錯誤要留痕）**可以同時滿足**，
  WARNING 就是那個交集。**既有的 fail-soft 也不是靜默的**——Gemini 失敗時是
  「記 ERROR、跳過、池不消耗」，本條原本的括號註解誤述了既有風格。
  型別錯誤（非 list／元素非字串）則直接 `RuntimeError`。推導見 `research.md` R1、
  契約見 `contracts/digest-pool.md` C1-2／C1-3／C1-4。
- **匯流清單含 `道安政策` 自己**：去重，不得重複計數。
- **匯流清單含另一個也有 digest 設定的類別**：本 spec 範圍內不會發生（只有 `道安政策` 有 digest），
  但行為必須明確——文章會被兩份 digest 都選到並重複消耗。**列為已知限制，不在本 spec 解決。**
- **匯流後 `effective_count` 仍低於 `trigger_count`**：不觸發，與現行行為一致。
- **兄弟類別文章已被其他機制排除（`excluded_links`）**：維持排除，匯流不得繞過既有排除。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: digest 池的組成 MUST 能由設定指定**一組類別**，而非固定單一類別。
- **FR-002**: 未設定匯流清單時，系統 MUST 表現得與本功能不存在時**完全相同**（預設關閉）。
- **FR-003**: 匯流 MUST 只作用於 **digest 選材階段**；文章自身的分類標記 MUST NOT 被改寫。
- **FR-004**: 匯流後的池 MUST 沿用既有的品質下限、選材上限與排除清單語意，不另立規則。
- **FR-005**: 經匯流進池並發布的文章 MUST 與原本就在池中的文章**一樣被標記為已消耗**，
  避免下週重複進池。
- **FR-006**: 設定中的匯流清單 MUST 在載入時被驗證（型別錯誤要明確報錯，而非靜默忽略），
  與既有 digest 設定的驗證強度一致。
- **FR-007**: 系統 MUST 在執行紀錄中留下匯流的**逐項足跡**——至少包含每個來源類別的貢獻篇數，
  使「匯流是否有效」不必查資料庫就能從 log 判讀。
- **FR-008**: 本功能 MUST NOT 引入任何 AI／網路呼叫（digest 選材位於純函數側，
  成本線見 `memory/project_daily_weekly_cost_boundary`）。
- **FR-009**: 報告的對外標題 MUST 維持既有形式，不因匯流而改變。
  這保住兩件事：報告的持久化鍵（週 × 標題）序列連續，以及讀者端不出現斷點。
  標籤在讀者關心的層級上本就涵蓋這些題材——科技執法設點、路權鬆綁、待轉區工程
  都是道路安全政策，taxonomy 拆開它們是為了分群，不是因為它們屬於不同領域。

### Key Entities

- **digest 池**：某週內、屬於指定類別集合、未被排除的文章集合。分三層——
  `pool_all`（全部，供消耗）／`effective`（過品質下限，供觸發判定）／`selected`（供選材）。
  ⚠️ **消耗的是 `pool_all` 而非 `selected`**（010 的「池歸零」設計，避免低分文章永遠累積）：
  發布成功後，**整池**都被標記為已消耗，包含從未進入報告的那些。匯流會放大這個差額——
  見下方 Assumptions 的 `max_articles` 條目。
- **匯流清單**：一組類別名稱，附加於既有的 per-category digest 設定之下。

## Success Criteria *(mandatory)*

**量測前提**：全部指標可在**既有 buffer 資料**上離線重播，不需等新資料、不需呼叫外部服務。
硬門檻只收 **E1 實測**。基準取自 2026-08-10 週窗（`buffered_at ≥ 2026-08-04`）。

### SC-001 承重解除（本 spec 的主要目標）

**階梯**（Gate 設在最寬鬆那階，每階錨定一個真實場景）：

- **SC-001 L0 / Gate**：匯流後 digest 池的 `distinct_sources` **嚴格大於**匯流前。
  錨定：08-10 實測 **3 → 9**。寬鬆到只要匯流帶進任何一個新來源就過。
- **SC-001 L1**：**抽掉最大來源後**，有效篇數仍 ≥ `trigger_count`。
  錨定：08-10 實測匯流後剩 **18 ≥ 10**（匯流前剩 9 < 10 → 不觸發）。**這一階才是「承重解除」本身。**
- **SC-001 L2 / 理想**：連續 4 週最大來源佔比 ≤ 50%。
  錨定：08-10 實測匯流後 **60.9%**（匯流前 75.7%）——**目前未達成**，需要更多來源或更多匯流類別。

### SC-002 內容不流失（承 012 SC-004 的教訓：用可歸因，不用零損失）

⚠️ **不要把這條寫成「現行選材不得掉出」。** 2026-08-10 實測證明那是**結構性不可達**的單一門檻：

`quality_score = keyword_match_ratio×0.4 + normalised_word_count×0.3 + source_weight×0.3`。
經 `source_defaults` 進池的文章**標題本來就沒有分類 token**（那正是它們 fallback 進池的原因），
於是 `keyword_match_ratio` 結構性偏低；而兄弟類別文章是**命中 taxonomy 關鍵字**才被分過去的，
該項結構性偏高。實測：匯流的 9 篇分數 **0.299–0.348**，現行選材墊底 9 篇 **0.193–0.199**——
**匯流文章整批壓過現行墊底文章**，擠出數恆為 9 且**與 `max_articles` 無關**
（25／30／35 三種設定實測皆擠出 9），因為 `effective`(44) 恆大於上限。

這與 012 SC-004 是同一個形狀（機制與門檻結構性衝突），故沿用同一個修法：

- **SC-002 L0 / Gate**：**每一筆**被擠出的現行選材都能歸因到「被分數更高的匯流文章取代」，
  **沒有無法解釋的消失**；且擠出數 ≤ 新進數。錨定：08-10 實測擠出 9 ＝ 新進 9，全部可歸因。
- **SC-002 L1**：被擠出者的分數**全部低於**新進者的最低分（純排序結果，無交錯）。
  錨定：08-10 實測擠出上界 0.199 < 新進下界 0.299，**無交錯**。
- **SC-002 L2 / 理想**：擠出數為 0（需 `max_articles ≥ effective`，即不截斷）。
  這一階是**編輯決定**而非工程問題——要不要讓報告變長。

**可歸因性是 L0 承重的那一條**：它把「損失」從一個數字變成一份診斷，
否則無法分辨「匯流擠掉了好東西」與「匯流用好東西換掉了填充稿」這兩種相反的情況。

### SC-003 雜訊誠實計入（不得為了好看而略過）

匯流會帶進離題內容——`路權政策` 裡有「頻變換車道.行駛禁行機車道 一查又是毒駕」這類刑案。
**相關性閘目前只有 `機車事故` 的規則，`道安政策` 走 fail-open，所以沒有任何東西擋它。**

- **SC-003（無階梯，是一個必須產出的數字）**：驗收 MUST 報出匯流帶進的離題篇數與比例，
  且**不得以「現況也沒擋」為由略過量測**。這個數字是 BACKLOG #7（政策 token 表）的動機依據。
  **判讀方式＝人工逐篇**：匯流每週僅帶進約 9 篇，不需要 012 那種標記基準集；
  但**判讀結果 MUST 寫進驗收紀錄**（哪幾篇、為什麼算離題），否則下次無法比較。

**這不是本 spec 的阻擋條件**——匯流前的池同樣沒有相關性閘，本功能沒有讓情況變差。
但把數字記下來，#7 才有可校準的起點。

## Assumptions

- **編輯決定已作出**：使用者於 2026-08-10 明確選擇「匯流兄弟類別」而非「維持窄定義、改補來源」，
  並確認報告涵蓋範圍變寬是預期結果。本 spec 不重開這個問題。
- **初始匯流清單＝`路權政策`／`科技執法`／`交通工程`**。`行人事故` 與 `路口安全` **刻意不納入**——
  它們的內容以事故為主（`停讓行人` 的 11 篇落在 `行人事故`，其中含大量事故簿），納入會把
  digest 從「政策彙整」變成「事故彙整」。這是可調的（FR-001），但預設保守。
- **不改分類法**。`道安政策` 的三個關鍵字與兄弟類別的關鍵字**都不動**——匯流發生在下游，
  細分類在 buffer list 仍然有用。
- **不改 `max_articles`（維持 25）** — 2026-08-10 澄清後**確認保留**，且理由已從「這是獨立決定」
  補強為實測依據。因為消耗的是 `pool_all`（見 Key Entities），匯流會把「被消耗但從未發布」
  從 **12/37（32%）推高到 21/46（46%）**。這看起來像在破壞本 spec 想救的內容，但實測顯示不是：
  兄弟類別那 9 篇分數 **0.299–0.348，全部落在 top 25 之內**（新進榜 9/9），
  **多出的消耗全部是 `交通安全教育` 的低分填充稿**（0.193–0.199，如「監理所推交通桌遊」
  「學童化身一日小警察」）。本 spec 要救的內容一篇都沒被犧牲。
  調高上限會改變報告長度與 LLM 輸入成本，屬獨立的編輯決定；「池歸零」則是 010 的刻意設計，
  推翻它會讓低分文章永久累積，兩者皆列為範圍外。
- **量測窗＝週**，與既有 digest 的窗一致；不引入新的時間語意。
- **重複文章**：實測發現匯流新進的 9 篇中有 2 組近似重複（同事件不同媒體）。
  既有 `embed_dedup` 在 buffer 階段處理，本 spec **不新增去重邏輯**，但驗收要記錄殘餘重複數。

## 已知限制（誠實標註）

- **n 小**：SC-001 的錨定值來自**單一週窗**（08-10，兄弟類別僅 9 篇）。三週合計 33 篇。
  承重判定（18 ≥ 10）有餘裕，但「連續維持」未經驗證——SC-001 L2 正是為此而設。
- **兄弟類別的量本身可能不穩**：`交通工程` 本週僅 1 篇、三週僅 5 篇。若某週三類皆空，
  匯流的效果為零，承重會回到匯流前的狀態。**這不是缺陷，是本解法的天然上界**——
  它把既有內容用滿，不會無中生有。真正要更多來源時，仍需回到 #8 的原計畫。
- **雜訊無擋**：見 SC-003。
